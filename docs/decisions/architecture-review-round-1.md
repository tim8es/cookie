# Архитектурное ревью — раунд 1

**Статус:** R1–R3 согласованы 2026-11-14; R4/R5 и детали ADR пока PROPOSED. **Фаза:** F0, код не разрешён.
**Задачи:** #8 (PRD), #9 (kernel), #10 (stack), #11 (booking), #12 (identity), #13 (UI), #15 (F0 gate).
**Референсы:** ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0006.

## Рамка
Сначала принимаем важные продуктовые ограничения и степень динамичности модулей. Только затем утверждаем детальные API и реализацию. Рекомендации в этом файле не считаются решениями пользователя.

### R1. Способ подключения модулей
**Рекомендация:** версионируемые модули как пакеты в монорепозитории с регистратором на этапе сборки; на уровне компании включаются/выключаются через configuration/entitlements. На self-hosted можно поставить отдельный согласованный комплект релиза, без форка бизнес-логики. Новая версия модуля допускает обновление/redeploy.

**Альтернатива:** hot-install в работающий сервер без пересборки и перезапуска. Это потребует sandbox/untrusted code policy, hot migrations, dependency resolution и значительно усложнит сопровождение; не рекомендовано на старте.

**Ответ владельца (ACCEPTED 2026-11-14):** имеющиеся в SaaS модули включаются по салону без перезапуска; новый исполняемый модуль выкатывается поставщиком через release, self-hosted обновляется штатной процедурой. Hot-install произвольного кода не нужен в F1/F2.

Связанные: #9, #17, #35–36.

### R2. Сложность первой брони
**Рекомендация:** F1 = один филиал в организации, одна услуга и один мастер на запись, фиксированная длительность, рабочие смены, перерывы и исключения. В схеме заранее предусмотреть locationId и расширяемость состава брони, не реализуя сразу multi-service/multi-resource.

**Альтернатива:** несколько услуг/мастеров/ресурсов в одной транзакции уже F1. Это сильно усложнит поиск и блокировку доступности.

**Ответ владельца (ACCEPTED):** одна услуга и один мастер на бронь; другие услуги бронируются отдельно. Предел в один филиал для F2 **не утверждён**, вынесен в следующий раунд.

Связанные: #8, #11, #20–23.

### R3. Клиентская идентификация
**Рекомендация:** автоматический CRM Customer при бронировании, без отдельной регистрации. Web-guest вводит телефон (email необязателен); безопасное управление записью — по краткоживущей подтверждённой ссылке или OTP, не только ID/телефону. Telegram initData проверяется сервером; телефон Telegram автоматически не передаёт.

**Альтернатива:** разрешить при настройке салона брони только с проверенным Telegram ID без номера (с последующей возможностью привязки контакта). Это снижает трение, но ограничивает альтернативные напоминания и связь с клиентом.

**Ответ владельца (ACCEPTED):** клиент сам выбирает телефон или Telegram; телефон при подтверждённом Telegram-входе не обязателен для регистрации. Настройка салона на обязательность телефона для конкретной услуги — отдельное открытое требование.

Связанные: #12, REQ-005.

### R4. Технический стек
**Рекомендация:** сохранить Go vs Node.js/TS на backend; Svelte 5 + Vite static первичный frontend-кандидат, React контрольный. Возможность SvelteKit SSR обосновать нуждой SEO/public showcase. F0 — документальные критерии; только с отдельного разрешения в F1 выполнять короткий benchmark spike.

**Вопрос:** согласен с условным shortlist до F1 или нужно выбрать один backend runtime окончательно без инженерного сравнения?

Связанные: #10, #13, #16.

### R5. Multi-tenant и self-hosted
**Рекомендация:** SaaS изолирует много компаний через tenants; self-hosted по умолчанию одна компания в отдельном экземпляре. Один пользователь может иметь разные роли в разных компаниях. ПДн граждан РФ храним с учётом локализации и применимых требований. Altare только для демонстраций на синтетических данных до правовой проверки.

**Вопрос:** достаточно ли одной компании и одного филиала в одной self-hosted инсталляции первого релиза?

Связанные: ADR-0004/0006, #12, #35–37.

## Результат обсуждения R1–R3 (13.11.2026)
- **R1:** пользователь предпочёл B, поскольку SaaS-клиент не должен перезапускать сервер при покупке функции. Требование безрестартной **активации установленного кода для организации — ACCEPTED**. Операторский deploy **нового кода**, а не hot-install в запущенный монолит — ACCEPTED 2026-11-14. Общий SaaS runtime может обслуживать много организаций с tenant isolation, нет инсталляции на каждый салон.
- **R2:** ACCEPTED — одна услуга/мастер в одной записи; следующая услуга — отдельная бронь. Связанные услуги как рекомендации поддержаны концептуально, F2 optional module — предложенная реализация. Не делать multi-service агрегат в F1.
- **R3:** ACCEPTED — сайт предлагает телефон или Telegram, бот/Mini App использует Telegram без обязательного телефона. Email не обязателен. Phone ownership check/OTP, Telegram website OIDC/PKCE и linking прорабатываются в ADR-0004.
- **R4/R5:** прежние предложения остаются без отдельного утверждения. Права, филиалы и структура организаций вынесены в Round 2.
