# F1: планирование будущих смен владельцем

Владелец с подтверждённой серверной Telegram-сессией выбирает мастера, существующее назначение в филиал и локальные начало/конец будущей смены. Web API сохраняет черновик в PostgreSQL и показывает его в разделе «Расписание». Нет активации услуги, назначения или bookable профиля.

- Используется существующий scheduling draft command, receipt, mutation audit и outbox, а не отдельный booking engine. Обычное внутреннее создание смен и edit/approval/publish не меняют стандартные требования. Новый owner-plan mode отдельно защищён owner-only permissions `schedule.shift.plan.read/create` (0029). Запрос не может назначить себе права или передать tenant/actor/status.
- Staff-first mutation lock, актуальная роль/bearer/link и IANA zone филиала удерживаются до commit; нет policy-first внешней транзакции над staff-locked командой. Для планирования допускается уже созданное неактивное назначение только у активного, но не bookable профиля. Никаких изменений availability после сохранения.
- Сервер разрешает гражданское локальное время в UTC через IANA и отклоняет DST gap/fold; будущее, положительная длительность до 48 часов. Повторный ключ возвращает ту же квитанцию, изменённый payload конфликтует. List показывает до 200 ближайших будущих невключённых draft shifts с явным признаком переполнения, не disabled/published историю.

Границы: F1 календарь отдельных смен, не недельные повторяющиеся графики, редактирование/удаление/публикация, перерывы, исключения, entitlement/approval workflow или реальная доступность. Они отдельно требуют соблюдения безопасности Booking и согласованных продуктовых решений. Не включать real PII, публичную запись или Altare production, не закрывать #20/#203 по этому срезу. Техническое решение owner-only планирования допустимо к независимому review, не делегировать права мастерам/администраторам автоматически.
