## Правила применения и критерии полноты

- Источник истины — [PRD](../product/requirements.md), названия и правила здесь сжаты для навигации. Если краткая строка теряет нюанс, исполняется полный PRD и принятый DEC.
- В [стратегии тестирования](../quality/test-strategy.md) есть содержательные сквозные тесты, но не у всех 67 требований есть прямой отдельный индекс `REQ → test ID`. До F1 задача владельца соответствующего Issue — дополнить тестовые ID, негативные сценарии и проверку доказательствами. **67/67 = полнота навигационной трассировки, не тестовое покрытие.**
- F1 — внутренний технический срез, Pilot — подмножество F1+F2 для первых салонов, F2 — целевой продаваемый пакет. `Pilot/F2` обозначает лицензирование, а не автоматическое включение всех F2 модулей в пилот.
- Обязательны настоящие PostgreSQL integration/concurrency tests для double booking, атомарных скидок, scheduling update и единой authZ по каналам; mocked UI tests недостаточны.
- Отдельно проверить на пилоте: web и Telegram, outbox notifications, 30 календарных дней с регистрации, индивидуальное предложение ДО регистрации, отдельный paid opt-in, ограниченный режим и сохранение Confirmed и экспорта, unique bookable masters и no Booking quotas.
- Строки REQ-038–056 не следует самовольно превращать в пилотный блокер: они остаются принятыми требованиями полного F2, если не выбрана скидочная функциональность для самого первого пилота.

## Следующий инженерный DoR

Для каждого F1/Pilot Issue при переходе Ready указывать: REQ ID, accepted DEC, ссылку на ADR/contract, точный success+failure AC, negative auth/money/concurrency test и зависимость. Случаи без согласованного правового/коммерческого основания блокируют **реальный пилот**, но не написание кодового тестового среза после отдельного owner approval.

**Результат:** 67/67 строк присутствуют, числовая последовательность REQ-001–067 без пропусков.
