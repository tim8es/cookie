# F1 verified-session HTTP guard (Issue #18, partial)

**Mode:** internal engineering scaffold with synthetic test sessions only. The production API bootstrap does **not** install a session verifier, so the protected context route is **not registered** in normal `main.ts` startup. This does not authorize real users, customer data, commercial pilots or a public deployment.

## Route contract
- When **explicitly** supplied with `ProtectedSessionDependencies`, the app registers `GET /v1/organizations/:tenantId/session-context` (read-only, responds with the verified tenant ID only).
- Authorization must use a Bearer token passed to a trusted `BearerSessionVerifier`. No raw JSON, `x-user-id`, `x-tenant-id` or query parameter is treated as identity.
- The verifier interface must return validated identity ID, selected tenant ID and expiry. The server additionally enforces UUID format, finite expiry in the future and exact match between the selected tenant in the URL and the verified session.
- `TenantPolicyGuard` checks the hardcoded technical permission `organization.context.read`. With `postgresTenantPolicyGuard`, the existing PostgreSQL-backed policy+audit denies absent membership, wrong tenant and missing roles.
- Error mapping: missing/bad/expired credentials `401`; tenant mismatch or known policy denial `403`; policy storage/audit faults `503`, without driver errors or secrets.
- Correlation ID is generated by the API and must not be sourced from a caller-controlled header.

## Coverage
Fastify injection unit tests cover default route absence, forged headers, malformed Bearer, verifier failure, expiry, wrong tenant URL, verified actor scope, denied permissions and storage failures. No real tokens are issued or accepted.

## Remaining gates
- **No real AuthN provider is wired.** Before any live client access, implement token signature/issuer/audience/expiry/revocation checks, tenant session selection, credential linking, secure OTP/Telegram adapters, rate limiting, audit retention, cookie/CSRF considerations and permission matrix review.
- Real commands/queries must use trusted tenant-scoped repositories and recheck permissions inside their mutation transaction. This diagnostic route **does not** create a Booking or change business data.
- Customer/StaffProfile resource relationships and fine-grained field-level DTOs remain pending. PostgreSQL RLS, service DB role privilege hardening, end-to-end security/PII and RF legal assessment remain explicit pre-pilot requirements.

Current implementation is intentionally smaller than Issue #18 acceptance; leave the issue open.

## F1 #165 — transactional revocation guard (synthetic Cookie bearer)

**Status: F1 engineering proposal awaiting independent review / exact-head CI.**
The verified `cs_` bearer is SHA-256 digested inside the trusted HTTP
AuthN adapter after its verifier succeeds. The raw bearer and its digest
must never be logged, exposed or accepted as user-supplied actor fields.
Trusted non-Cookie synthetic bearer adapters remain covered by their own
separate test-only AuthN contract; they cannot be promoted to production
without equivalent transactional revocation protection.

Protected Booking Create/Cancel/Reschedule commands call
`requireTenantPermission` **inside the same transaction** as the mutation,
receipt and Outbox. For a Cookie bearer that guard first performs an
unlocked discovery of the optional Telegram link (not authoritative), then
obtains a SHARE lock on the active, verified/consented link, **before**
obtaining a SHARE lock on the exact non-revoked and unexpired opaque session.
The guard first acquires the established organization → membership →
assignment → role locks, then the fixed Telegram link → session locks.
This also matches the membership-disable trigger's membership → session
UPDATE order and avoids lock inversion against both revocation triggers.
Under PostgreSQL READ COMMITTED, the final session check is re-evaluated
after any concurrent revoke; all locks survive Booking COMMIT/ROLLBACK.
A successful
revoke-first COMMIT denies the transaction before any Booking write or
receipt. In the command-first order, revoke must wait for commit.

The same check is used by protected workspace-context reads; the concrete
Postgres session-context policy adapter now holds a transaction around its
lock/policy checks. Read endpoints that already call `requireTenantPermission`
within transactions inherit this protection.

No live public Cookie auth, Telegram provider delivery, production routes,
real identities/PII, payments or production deployment are enabled. A
separate approved AuthN/Customer ownership/security review is mandatory.
