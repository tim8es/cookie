# Controlled staging customer identity (F1 #18/#203)

Operator-only atomic allocation of a synthetic Client Identity, tenant membership, minimal context-only role, Customer and verified consented channel binding. Existing/revoked channel mappings cannot be repurposed, owner never receives the client role via this flow. The association is unique within tenant and references the exact consented Telegram link. Operator CLI reads signed proof from stdin with explicit synthetic acknowledgement and consent; never stores raw proof. No automatic signup, real PII, guest linking, multi-tenant selector, public booking, or commercial trial.

With explicit staging flag and real Telegram provider, GET staging-customer-context uses bearer transaction revalidation, client-only permission and the exact minting link. No supplied customer ID, role or tenant authority from browser. Query string surface=customer-staging chooses presentation only; same server HMAC exchange and fresh context; invalid context revokes bearer, no owner fallback or browser storage. Independent review and #113/#165 gate still needed before actual Booking API. The current context role grants no booking mutation or read permission.

CI fixtures are purely synthetic; actual Telegram device/Altare and full consent evidence remain out of scope. To exercise in private synthetic staging use COOKIE_OPERATOR_STAGING_CUSTOMER=synthetic-only-acknowledged, COOKIE_TELEGRAM_LINK_CONSENT=confirmed, COOKIE_STAGING_TENANT_ID and configured DB/secret/server bot credentials; pnpm db:link-staging-customer reads fresh signed proof on stdin. Never put proof in command arguments or logs. No production rollout.
