# Дорожная карта: от документов к продаваемому продукту

**Статус: PROPOSED.** Никаких обещанных дат: последовательность зависит от review и рисков, а не от оптимистичного календаря. Приоритеты в Issues; дорожная карта не заменяет их.

## Логика фаз
~~~mermaid
flowchart LR
    F0["F0: Подготовка и ревью"] --> G0{"Docs approved?"}
    G0 -->|Да| F1["F1: Вертикальный технический срез"]
    G0 -->|Нет| F0
    F1 --> G1{"Reliable booking?"}
    G1 -->|Да| F2["F2: Продаваемый продукт"]
    G1 -->|Нет| F1
    F2 --> G2{"Security + paid pilot?"}
    G2 -->|Да| F3["F3: Расширения по спросу"]
    G2 -->|Нет| F2
~~~

### F0 — Documentation baseline / **текущий этап**
Эпик #1; задачи #8–#15. Выход: согласованный PRD/UX пути, дифференциация, архитектура modules/core, proposed & accepted ADRs, stack, security, экономическая гипотеза, связанные Issues и правила разработки.

**Gate F0:** owner ознакомился с draft PR, внёс замечания, все блокирующие решения получили ACCEPTED или сознательный non-blocker status, нет противоречий и orphan features; docs PR слит. Для стека возможно условное решение на документальных критериях с ограниченной валидацией как первой F1 задачей #16. Никаких coding spikes до явного разрешения пользователя начинать разработку.

### Принцип поставки: модульная основа, минимум функций на старте (ACCEPTED DEC-093 / REQ-057)
- Масштабируемость и модульные границы проектировать **с первого технического среза**, но не пытаться одновременно реализовать и показать все модули.
- Первый пилот может использовать лишь минимально достаточный набор готовых возможностей для реального сценария записи и управления салоном. **Это не отменяет** целевые требования полного F2 (например, multi-location, безопасность, SaaS/self-hosted и согласования графика), но позволяет отделить **пилотный срез** от **завершённого F2 Gate**.
- Optional add-ons и расширенные настройки не должны усложнять первоначальный кабинет. Новые модули включаются/появляются по мере готовности и прав организации; изоляция функций соблюдается на сервере, не только в UI.
- Обсуждать с владельцем **крупные продуктовые развилки и границы пилота**. Низкоуровневые comparator/schema/UX mechanics оставлять PROPOSED до технического review, если нет реального продуктового конфликта.

### F1 — Технический end-to-end срез (не продаётся)
Эпики #2 и #3; задачи #16–#23.
- Platform: #16 условный tech spike (только если согласован и после F0 Gate) + bootstrap/CI, #17 kernel, #18 identity/tenancy/policy, #19 persistence/jobs.
- Domain: #20 catalog/staff/scheduling, #21 booking consistency, #22 API/events.
- Interface: #23 technical booking UI + business calendar.
**Gate F1:** сквозная запись в Postgres через web, конкурентные тесты, tenant/role safety, отказ дополнительного модуля не ломает booking. Есть воспроизводимые тесты.

### F2 — Первый коммерческий продукт
Эпики #4–#6; задачи #24–#39. Параллельные потоки после F1:
- Пользовательский опыт: #24 общий UI web/widget/Mini App **с выбором филиала**, #25 клиентский профиль/повтор/перенос, #26 admin workspace **с несколькими филиалами одной организации**, #27 темы/onboarding, #28 отчёты и настраиваемое совместное применение скидок/промокодов. Филиалы имеют разные часы/адреса/календарь, CRM организации общая.
- Каналы и расширения: #29 Telegram, #30 notifications, #31 AI add-on, **#32 настраиваемое изменение графика и базовые согласования (F2 обязательно)**, #33 интеграции карт с обязательным feasibility gate, #34 staff/admin chat, #44 опциональные рекомендации связанных услуг.
- Поставка и бизнес: #35 entitlements/SaaS, #36 self-hosted, #37 безопасность/ПДн, #38 эксплуатация, #39 интервью/пилот/pricing.

**Gate F2:** самостоятельная настройка измерена, мультифилиальность, права на филиалы и оба режима изменения графиков с проверкой конфликтов подтверждены, записи и права проверены, backup/restore, российские ПДн и hosting разрешены, есть полный список платных/бесплатных функций и реальные предложения для пилотных клиентов. Функции с закрытым API карт не обещаем до разрешения. Состав реально продаваемого пакета утверждается только после пилота.

### F3 — По сигналам спроса
Эпик #7; #40 MCP, #41 voice/other messaging, #42 расширенная loyalty/finance/stock. Не блокируют F2.

## Приоритеты
- **P0** — обязательные условия перехода в следующий этап: security, архитектура, атомарная бронь, документальный freeze.
- **P1** — коммерчески важные функции и UX, в том числе отдельные add-ons.
- **P2** — перспективные расширения после подтверждения спроса.
- **P3** — идеи без достаточного подтверждения, не создают обязательств.
