# ADR-0004 — Личность, организации, клиенты и доступы

**Статус: ACCEPTED (F0 baseline 2026-11-14, owner approval)**; конкретная реализация, негативные интеграционные тесты и legal/operational evidence остаются обязательными на следующих этапах. · Issue #12 · REQ-005,007,016.

## Разделяем сущности
- Identity: кто аутентифицирован (пользователь).
- Membership: роль пользователя в организации, допускается несколько ролей/организаций.
- Customer: профиль посетителя **в рамках конкретной организации**, необязательно зарегистрированный пользователь.
- Channel identity link: подтверждённая привязка Telegram user к Identity/Customer с учётом правила согласия.
- Guest booking token: scoped, limited lifetime/replay, разрешает только строго обозначенное действие.

## Мультифилиальность (ACCEPTED для F2)
- Organization — граница tenant для SaaS, объединяет **несколько** Locations. Один Identity может иметь роли в разных организациях.
- CRM Customer принадлежит Organization, история посещений связывается с филиалами через Booking.locationId; не смешивать CRM разных organizations.
- Membership может иметь организационную область действия или scope только назначенных Locations. Конкретные матрицы owner/manager/admin/staff требуют дальнейшего решения.
- На backend проверять не только tenantId, но и доступ к конкретному locationId и целевой записи. UI-фильтр «мой филиал» не заменяет authorization.

## Ролевая модель — решение 2026-11-14
**ACCEPTED:** вариант Б: стандартные типы ролей и ограниченное конфигурирование отдельных разрешений с областями организации/филиалов. **ACCEPTED:** type/code, displayName и должность/специализация сотрудника — независимые поля.

- RoleType/baseType — стабильный технический идентификатор защищённого шаблона, не редактируемая «должность».
- OrganizationRole — roleId, organizationId, baseType, displayName и разрешённые overrides прав. Название владелец может менять без изменения baseType. Допускаются именованные варианты одного типа при соблюдении security guardrails.
- Membership/RoleAssignment — связь Identity с конкретной OrganizationRole и scope Locations. Авторизация решается по permission codes и контексту ресурса, **никогда** по displayName или positionTitle.
- StaffProfile.positionTitle описывает специальность для бизнеса/клиента; не выдаёт разрешения.
- Owner и transfer ownership — защищённая процедура, не обычный настраиваемый переключатель. Владелец, работающий мастером, может иметь StaffProfile, но полномочия и услуга остаются независимыми.
- Принцип **default deny** для невыданных permissions и недоступных филиалов, серверное enforcement в API, событиях и агентских инструментах.

**Открытые детали:** каталог permission codes; конкретный алгоритм effective permissions при нескольких ролях (рекомендация изложена ниже); права на контакты клиентов и самостоятельное редактирование графика; аудит изменений ролей. Отдельно проверить злоупотребление сменой названия, эскалацию прав и cross-location IDOR.

## Множественные роли и филиальные области действия (ACCEPTED, 2026-11-14)
- Один Identity может иметь Membership в разных организациях, а внутри одной Organization — **несколько независимых RoleAssignments**. У каждого назначения собственные roleId и location scope; в филиале A пользователь может быть одновременно staff и administrator, а в филиале B — только staff.
- Отображаемое название OrganizationRole и StaffProfile.positionTitle не участвуют в policy evaluation.
- **Предлагаемый алгоритм (PROPOSED):** для запроса сначала установить доверенные identityId, tenantId и locationId; выбрать только активные RoleAssignments данного Membership, включающие locationId; объединить их разрешённые permission codes; далее проверить resource ownership, специальные restrictions и entitlement. Для чтения по организации разрешение organisation-wide должно быть явно выдано, а не выведено из наличия доступов к двум филиалам.
- **Default deny:** отсутствие разрешения, отсутствие назначенного филиала или конфликт с политикой ресурса ведёт к отказу. Реализация deny-overrides и системных non-delegable permissions ещё на ревью.
- **Security tests:** администратор A/мастер B не получает admin-права в B через прямой API, chatbot, worker или AI tool; права не растут из-за переименования роли, токенов другого tenant и собственной смены membership.

**Нерешено:** точная матрица permission codes, возможность явных deny, scope контактов клиентов, безопасность изменения собственных role assignments, мультифилиальная работа мастера.

## Видимость клиентских данных для мастеров (ACCEPTED product / PROPOSED enforcement)
**Утверждено 2026-11-14:** мастер видит только собственные визиты и клиентов, связанных с его записями, внутри разрешённых филиалов. Дополнительная видимость **номера телефона, истории визитов и заметок** управляется отдельными разрешениями владельца организации. Доступ ко всей CRM филиала базовой ролью staff не выдаётся.

**Предложенная модель:** staff-связь с клиентом определяется сервером по назначенным бронированиям/визитам и действующему Membership + locationScope. При запросе Customer контекст должен проверять staffId, booking/visit relation, locationId и purpose, а не только customerId. Мастер с дополнительной ролью administrator может отдельно получить права на CRM соответствующего филиала: ограничение прав применяется в конкретном tenant/location контексте.

**Примеры предполагаемых permission codes:** customer.contact.phone.view.assigned, customer.history.view.assigned, customer.notes.view.assigned. Отсутствующее разрешение = скрыть поле на уровне serializer/API response, исключить из поиска, отчётов, выгрузок и AI/Telegram context. При увольнении, отзыве права, смене исполнителя или филиального scope доступ прекращается. Требуются негативные tests через все каналы.

**Ещё не утверждено:** длина и подробность доступной мастеру истории (включая записи к другим мастерам), классификация внутренних заметок, ретенция/аудит доступа к контактам. Отдельные расширенные права администратора и owner не смешивать с правами staff.

## Мастер и филиальные назначения (ACCEPTED 2026-11-14)
- Один StaffProfile в рамках Organization может обслуживать несколько Locations; StaffLocationAssignments не создают отдельные Identity или StaffProfile и сами по себе не дают административных разрешений.
- Membership и scoped RoleAssignments определяют, какие операции мастеру доступны в каждом филиале. Единая рабочая загрузка для мастера составляется только из доступных ему по политике назначений/записей.
- Назначение работы в другом филиале не расширяет доступ к CRM всего филиала; права на клиентов сохраняются ограниченными своими записями, если нет отдельной scoped administrator роли.

## Решение
AuthN — отдельный platform provider. AuthZ — централизуемый policy contract, но проверяемый в каждом business command/query. Tenant context сервер извлекает из доверенных claim/session/link и сопоставляет с Membership; клиент не может сам назначить tenant простым request body. В SaaS данные разделяются tenant_id и фильтрами/constraints; дополнительный PostgreSQL RLS рассмотреть как defense in depth, не замену unit/contract tests. В self-hosted модель сохраняется.

## Контактные данные
Сбор минимального контакта во время записи, аккаунт необязателен. Для входа через Telegram сервер сверяет signed initData/auth_date; web-flow для существующей записи требует проверку владения контактом/короткоживущую ссылку, не просто номер или ID.

## Варианты входа, согласованные с владельцем
Клиент выбирает **номер телефона** либо **Telegram**, без обязательной отдельной регистрации перед записью; email не обязателен. CRM Customer scoped к салону создаётся при первой записи, а аутентифицированный Identity связывается с ним по подтверждённому основанию.
- Telegram bot: сервер использует доверенный Telegram update и Telegram user ID; username не является устойчивым ключом. Не создавать единую клиентскую CRM-базу всех салонов.
- Telegram Mini App: на сервере проверять raw initData и auth_date.
- Публичный сайт: актуальный Telegram Login поддерживает OpenID Connect Authorization Code Flow с PKCE и серверной проверкой ID token; старый iframe widget не выбирать как baseline без причины. Официальный источник: https://core.telegram.org/bots/telegram-login
- Вход по телефону: подтвердить владение номером, например одноразовым кодом. SMS/voice-провайдер и экономика — открытые вопросы.
- При входе через Telegram номер не требуется только ради регистрации. Если для конкретной услуги нужен телефон, салон может запросить его с объяснением.
- Безопасное связывание Telegram ID и проверенного телефона с Identity, без перехвата чужой записи по совпадающему имени/непроверенному номеру; возможность отвязки.

## Согласия и ПДн
Обработка записи и маркетинговые согласия — отдельные основания/сценарии. Сроки, экспорт, удаление, внешние LLM и размещение в РФ требуют review и юридической консультации перед коммерческим запуском.

## Проверки
Role matrix, cross-tenant IDOR, guest token replay, Telegram forged initData, actor impersonation через AI/MCP, audit of writes. Протестировать до F2.

## Рекомендуемая authZ модель для пакетного owner-review (PROPOSED F0-P06, 2026-11-14)
- `Identity` отдельно от Organization Membership/RoleAssignment и `Customer` внутри tenant; один user может иметь scoped roles в нескольких филиалах/организациях. Роль отображаемым названием не даёт привилегий.
- Effective allow = union **только** активных явно выданных permission codes для текущего доверенного tenant/location; после union применяются **hard** restrictions по resource ownership/field-level visibility и tenant entitlements. `default deny` для неразрешённого и отсутствующих scopes; Owner transfer и owner-only protected actions не выдаются обычным admin/self-service.
- Клиент/guest может читать и изменять **только свою** Booking по verified identity/short-lived scoped token; авторизация только по ID или непроверенному телефону запрещена. Staff видит только собственные связанные визиты и клиентов, телефон/история/заметки требуют специальных выданных прав; сервер фильтрует все экспорты/поиски и bot/API ответы.
- Phone OTP и Telegram OIDC+PKCE/initData проверяются сервером; credential linking требует verified proof. Конкретные OTP provider, юридические основания ПДн/retention, enum permissions и протокол Owner transfer — технический/юридический review, не выдуманный ACCEPTED.
- [Blueprint §2](f0-implementation-blueprint.md) содержит стартовую матрицу owner/admin/staff/client; #12 остаётся открытым до reviewer sign-off.

## Запись об утверждении F0 — 2026-11-14
Владелец явно **утвердил пакет F0-P01–F0-P12 как архитектурный baseline** и отдельно разрешил начать F1 (bootstrap, CI, PostgreSQL, основа приложения). В рамках этого ADR приняты архитектурное направление, границы и критерии тестирования. **Не подтверждены исполнением**: SQL concurrency, нагрузка, мобильный UX, реальные security tests, ПДн/платежи, закрытые provider APIs и коммерческие продажи. Требования к отсутствию пилота/реальных ПДн до отдельного согласования сохраняются. Изменение baseline через новый ADR/PR, не молчаливым коммитом.
