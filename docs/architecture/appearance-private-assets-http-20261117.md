# Private Appearance asset HTTP candidate

Refs #223/#203. No ordinary runtime activation. The real HTTP adapter is explicitly registered only by the integration harness. It accepts raw binary PNG/JPEG/WebP with exact Content-Type and no Content-Encoding, per-route 2 MiB body limit, one admitted upload per API instance (no queue); JSON/multipart/external URLs are not accepted. Bearer session with actual PostgreSQL opaque authority and appearance.manage permission must pass before parsing; the session and permission are checked again after bounded child normalization and within the storage transaction. All reads require appearance.read and trusted tenant/kind scope. PNG-only bytes, no-store, nosniff. Upload receipt is metadata only, no embedded secret or public URL. Existing draft compare-and-swap can accept the asset via actual ownership adapter; upload itself does not alter/publish the draft.

Storage uses an explicit positive operator-supplied count and byte quota, not a product default or commercial tier. READ COMMITTED tenant-scoped advisory transaction lock serializes quota writers across API processes; exact duplicates consume no additional capacity. All private upload writes must use that path. Trusted internal storage helpers are not public APIs. Identity authorization audits are retained; an explicit asset lifecycle audit/retention policy remains open. No automatic GC/deletion.

Remaining gates: hard OS-level codec privilege/network/native-memory isolation, externally enforced ingress/time/rate limits (slow uploads may occupy admission), bounded authenticated read concurrency, deployment-wide admission policy, quota operator/configuration review, independent security review and actual compiled runtime/browser use. One instance's upload admission is not a cluster-wide rate limit. No public route or publication entitlement. Keep disabled in normal runtime.

Tests use real signed Telegram exchange and the actual subprocess/PG storage: upload, normalize, dedupe, quota rejection, unauthorized/foreign-tenant/wrong-kind access, draft reference, permission revocation and logout; no default runtime upload registration. Further deterministic concurrent quota and revoke-during-decode tests required before activation.
