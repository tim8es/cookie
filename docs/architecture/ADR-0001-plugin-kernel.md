# ADR-0001: Минимальное ядро, расширяемые модули и модульный монолит

**Статус:** Proposed (обсуждение). **Дата:** 2026-11-13.

## Контекст
Цель — быстро развивать продукт и кастомные установки, не превращая core в набор связанных доменных сущностей. Ориентир на принцип Everything is a Plugin из DeepSeek Harness / Cordis, но без прямого переноса его реализационных деталей.

## Решение
**Одно развёртывание, один монорепозиторий, минимальное kernel и отдельные внутренние плагины с явными контрактами.** Сначала модульный монолит, далее возможное извлечение отдельных модулей в процессы/сервисы при доказанной потребности.

### Что входит в kernel
- Реестр и загрузчик модулей, manifest, совместимость API/версий, dependency graph.
- Жизненный цикл модулей (инициализация, запуск, остановка).
- Контракт для предоставления и получения сервисов, команд, запросов, событий и extension points.
- Стандартизованный execution context с id запроса, tenant/principal/correlation ID; kernel не реализует учётные записи и не знает предметной области.
- Enforcement границ/capability-проверок при вызовах (конкретные правила предоставляют auth/policy-модули).
- Базовые health/diagnostics и точки регистрации наблюдаемости.
- Никаких понятий: салон, мастер, услуга, запись, скидка, клиент.

### Что НЕ входит в kernel
Пользователи и роли, организации и биллинг, база данных, расписание, бронирование, календарь, уведомления, транспорт Telegram, AI, UI, финансы, аналитика. Их реализуют platform/business/channel/extension-модули и адаптеры.

### Примеры модулей
**Platform:** identity, tenancy, policies, persistence, reliable-jobs/outbox, telemetry, feature-entitlements.

**Business:** organizations, catalog, staff, scheduling, customers, bookings, notifications, visits/payments-status, discounts, analytics.

**Channels/UI:** telegram-adapter, messenger-runtime, booking-web, business-web, embed-widget, public-pages.

**Extensions:** ai-assistant, employee-schedule-approval, maps-yndx, maps-2gis, loyalty, finance, mcp-server, voice-transcription.

Здесь «модуль» — логически автономный пакет и набор контрактов, а не обязательно отдельный процесс/БД или публикуемый динамический плагин.

### Границы
- Модули не импортируют внутренние классы/таблицы других модулей. Доступ — только по версионируемым публичным контрактам.
- Например, bookings зависит от публичных capabilities scheduling, catalog и identity/policies. Полная независимость бизнес-модулей не обещается.
- Каждый модуль владеет своей схемой/таблицами; прямые межмодульные запросы SQL запрещены.
- Операции внутри одного консистентного агрегата могут использовать одну транзакцию. Межмодульная реакция — события и надёжный outbox; внешние интеграции — идемпотентность, ретраи, дедупликация.
- Переход на микросервисы потребует переработки сетевых вызовов, контрактов согласованности, deployment/observability. Он не «бесплатен».

### Пример концептуального контракта модуля (псевдо-TS, НЕ выбор backend-стека)
```ts
interface CookieModule {
  manifest: {
    id: string;
    version: string;
    requires?: Array<{ capability: string; range: string }>;
    provides?: string[];
  };
  register(ctx: PluginContext): void;
  start?(): Promise<void>;
  stop?(): Promise<void>;
}
```

Пример иллюстрирует контрактные обязательства независимо от языка. Если в ADR-0002 будет выбран Go, используется эквивалент на Go interfaces, без обязательной поддержки JavaScript runtime в kernel.

При запуске модули собираются и включаются на уровне deployment, а доступность модулей для tenant задаётся отдельно через entitlements/config. Горячую загрузку произвольных сторонних плагинов в первом релизе не поддерживаем.

### Два независимых уровня модульности — ревью 13.11.2026

**Согласованное продуктовое требование:** бизнес подключает и отключает доступный модуль в SaaS-кабинете без рестарта и участия оператора. Это не означает, что SaaS должен загружать новый исполняемый код без deploy.

- **Установка/обновление кода (operator):** версионируемый модуль включён в общий SaaS release, обновления выполняются централизованно с миграциями и rolling/blue-green deployment. Для self-hosted новая версия модуля поставляется обновлением образа.
- **Активация для конкретного салона (tenant):** platform-модуль entitlements хранит права на модуль, лимиты, настройки и активность. После покупки/подключения в SaaS настройки вступают в силу сразу, без перезапуска. UI, API, jobs, events и AI tools должны проверять tenant entitlement и permissions на сервере.
- **Доступ конкретного сотрудника:** даже когда модуль активен, роль/permissions отдельно ограничивают операции.
- **Разделение организаций:** один SaaS backend и одна Postgres-инсталляция могут обслуживать множество компаний; данные разделены tenant scope и проверяемым authz. Не создавать контейнер и базу на каждого клиента по умолчанию.
- **Предусловия:** миграции и зависимости модуля готовы к моменту включения; включение add-on не должно запускать непроверенный SQL. Нужны compatibility, quotas, versioning и правила отключения без потери данных.
- **Изоляция недоверенного кода:** произвольные внешние плагины могут скомпрометировать весь multi-tenant процесс; их hot-install без развёртывания отложен, позднее возможен изолированный plugin worker.

**ACCEPTED 2026-11-14:** горячее подключение предустановленной функции для салона обязательно. Горячая загрузка *нового исполняемого кода* без управляемого SaaS release/self-hosted обновления не требуется для F1/F2. Остальные детали ADR-0001, включая конкретные контракты, остаются PROPOSED.

### Важные сценарии
**Бронирование:** одна authoritative booking boundary проверяет конфликт интервалов и атомарно фиксирует запись. UI, боты и AI используют один и тот же контракт бронирования. AI не пишет напрямую в таблицы.

**Согласование графика:** approval-модуль хранит заявку и решение; после одобрения вызывает защищённую команду scheduling. При конфликтах с записями действие блокируется до разрешения конфликтов.

**AI/чат сотрудника:** одна цепочка авторизации для web и мессенджеров, с подтверждениями на изменяющие/чувствительные операции, журналом действий и ограниченными scopes.

**MCP:** отдельный адаптер тех же read/write capabilities с явной авторизацией, rate limits и контролируемыми подтверждениями, не альтернативный незащищённый путь к данным.

**Карты:** adapters, зависящие от внешних API и правил площадок; ядро и booking не зависят от наличия интеграции.

**Общий frontend:** одна библиотека client booking UI и route/state-model, разные оболочки website/embedded/Telegram Mini App. Не предполагаем идентичность возможностей всех мессенджеров.

### Проверки архитектуры до кодирования
1. Запуск без optional-модулей.
2. Module contract tests и запрет прямых imports между реализациями.
3. Тест корректности booking при конкурентных запросах.
4. Изоляция tenant и permission tests для каждой команды.
5. Отказ/таймаут интеграции не ломает core booking.
6. Mock/pseudo remote adapter вместо локального контракта для одного модуля в интеграционном тесте — как ранний индикатор извлекаемости.

### Не принято
- «Большое core» с доменной логикой.
- Множество сетевых микросервисов в MVP.
- Универсальные динамические плагины с произвольным кодом и hot reload с первого дня.
- Дублирующие booking flows внутри Telegram, сайта или AI.

## Рекомендуемый F0 default для единого owner-review (PROPOSED, 2026-11-14)
- Оставить принятые владельцем границы minimal kernel без предметной логики, hot-install произвольного кода не нужен. Конкретизировать `manifest / registry / lifecycle / contract version / request context / diagnostics` на уровне платформенного пакета, не превращая kernel в Domain Booking/Identity/DB.
- Shared transaction context допускается через platform-port только для строго согласованных инвариантов; доменные модули не импортируют внутренние хранилища друг друга. Негативный contract test должен обнаруживать cross-module imports.
