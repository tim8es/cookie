# F1 — безопасное хранение и очистка opaque-сессий (Issue #153)

**Статус:** инженерный внутренний механизм, **НЕ подключён** к production/API/планировщику. Только синтетические PostgreSQL-тесты. Связанные ограничения: #18, #113, PR #146, PR #156.

## Почему нельзя сразу удалять отозванный токен

Таблица "cookie_identity.opaque_sessions" хранит как хеш bearer-токена, так и уникальный "telegram_exchange_sha256". Он не позволяет повторно обменять тот же Telegram HMAC на новую сессию. Удаление строки до истечения срока проверки HMAC создаёт окно replay.

В "telegram-init-data.ts" приняты **верхние** технические границы: "maxAgeSeconds <= 3600" и "maxFutureSkewSeconds <= 60". При синхронизированных часах верхняя граница повторной пригодности подтверждения — "issued_at + 3660 секунд". "PostgresOpaqueSessionMaintenance" требует **явную** конфигурацию "retentionSeconds >= 7200" (и <= 30 суток), чтобы дать запас. Это не утверждённая политика юридического хранения данных, а минимальная **безопасная техническая задержка**.

Не сокращать задержку после отзыва или expiry. "issued_at" должен оставаться неизменным; verifier и PostgreSQL требуют мониторинга расхождения часов. **При неопределённости синхронизации часов отключать purge** до устранения причины.

## Контракт

- "purgeBatch()" удаляет только "(expires_at <= DB now OR revoked_at IS NOT NULL) AND issued_at <= DB now - retentionSeconds". "LIMIT batchSize" (1–500) с "FOR UPDATE SKIP LOCKED", выбор oldest-first; возвращается только число удалённых строк, без идентификаторов или секретов. Не вызывать в транзакции бронирования/авторизации. Запускать повторно отдельным **будущим** supervised job с ограниченным бюджетом и метриками; такого scheduler-а этот PR не включает.
- "deleteInactiveMembership(tenantId, identityId)" выполняет "SELECT ... FOR UPDATE" на membership, не удаляет активное membership, удаляет **не более `batchSize`** устаревших сессий за один вызов (`FOR UPDATE SKIP LOCKED`), а при оставшихся сессиях (включая свежие proof digest или следующий пакет) возвращает "retained". Внутри завершённого последнего пакета удаление membership идёт в той же транзакции, без окна повторной выдачи токена. Повторные вызовы обязательны для большого backlog; статус "retained" сам по себе не означает активную сессию.
- Другие FK на membership (role assignments, доверенные Telegram links в PR #156 и т.п.) **не удаляются** этим модулем: попытка возвращает "blocked-by-dependencies" и откатывает удаление сессий. Владелец Identity обязан сначала безопасно обработать зависимые связи отдельным согласованным workflow. Не менять "ON DELETE RESTRICT" на "CASCADE" без отдельного review.
- Методы предназначены только для доверенного внутреннего процесса с DB-доступом. Никаких публичных эндпоинтов, пользовательского "tenantId", фонового включения, миграций, реального Telegram и реальных ПДн.

## Тестируемая граница

Синтетические PostgreSQL 16 integration tests: старые отозванные/истёкшие сессии удаляются порциями; свежие HMAC остаются зарезервированными, повторный exchange не проходит; активное membership удалить нельзя; удаление отключённого membership безопасно блокируется свежими сессиями и посторонними FK; конкурентная блокировка сессии не тормозит другой batch. "issued_at" в тестах искусственно состаривается **только** для проверки retention и не имитирует реальное течение времени verifier.

## Не закрыто

Реальная политика хранения и удаления ПДн, синхронизация времени, production supervision/алерты, составной удаляющий workflow для "role_assignments"/"telegram_identity_links", полноценная атомарность отзыва прав перед Booking write (#113). Эти вопросы не являются PASS и блокируют production.

**Не разрешено включение фоновой очистки:** у глобального `purgeBatch` сейчас нет подтверждённого плана PostgreSQL на большой таблице и индекса с ведущим `issued_at`; `LIMIT batchSize` ограничивает удаление, но не стоимость поиска/сортировки. Перед production необходимо согласовать индекс и EXPLAIN/нагрузочный бюджет, мониторинг часов, юридический срок хранения, orchestration зависимых Identity/Telegram-связей и контролируемый планировщик. Эти пункты остаются открытыми в #153 и не считаются PASS даже при зелёном F1 CI.

Обслуживание membership получает обязательный доверенный `runTransaction` из точки композиции (реализация `runSqlTransaction` в Platform DB). Результат удаления допустим только после подтверждённого COMMIT; Identity не импортирует Platform DB и не вводит циклическую зависимость. Планировщик обслуживания и его production-регистрация остаются вне F1-кандидата.
