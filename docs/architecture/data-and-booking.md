# Данные и инварианты записи

**Статус: PROPOSED.** Бизнес-инварианты обязательны; конкретная схема PostgreSQL не утверждена.

## Предметные сущности
Organization, Location, Staff, Service, StaffService, ScheduleRule, ScheduleException, Customer, Booking, Visit, PriceSnapshot, IdentityLink, AuditEvent. Tenant isolation применим к организациям и дочерним данным. CRM Customer и login Identity — разные понятия.

## Инварианты
- Сначала одна услуга, один специалист и один непрерывный период. Сложные цепочки услуг/оборудование позже по ADR. Каждая бронь содержит обязательные tenantId и locationId уже в F1; несколько филиалов одной организации реализуются в F2.
- Все интервалы сохранять как абсолютные даты/UTC; локальный IANA timezone **филиала** применять для отображения, расписаний и DST (при отсутствии отдельного timezone — значение организации по умолчанию).
- Доступность учитывает длительность, перерывы, исключения, отгулы и уже активные записи.
- Два параллельных запроса на пересекающийся интервал одного сотрудника не создают два активных бронирования.
- API поиска слотов даёт предварительный результат; при подтверждении клиентом CreateBooking заново проверяет ресурс и **атомарно создаёт сразу Confirmed** либо возвращает конфликт без активной брони.
- Повторы запросов с idempotencyKey в пределах tenant/actor не создают дополнительные брони.
- Изменения графика с существующими бронями требуют явного разрешения конфликтов; недопустимо молча отменять их.
- Сервер делает authorization на чтение/перенос/отмену, ссылки для гостей должны иметь ограниченный срок/подтверждение.

## Базовая цена и филиальные overrides (ACCEPTED product / PROPOSED price resolution)
- **ACCEPTED F2:** Organization управляет единым Service-каталогом. У Service есть базовая цена, а Location может иметь собственное значение цены для этой Service без её дублирования. Если переопределение отсутствует, действует общая цена.
- **PROPOSED:** эффективная стоимость перед подтверждением определяется на сервере в Catalog/Quote по (tenantId, locationId, serviceId), проверив доступность Service в этом филиале: explicit location price override → Service basePrice. Nullable override отличать от 0. Определённая цена не должна произвольно подменяться клиентским API.
- **PROPOSED:** сохранять PriceSnapshot в Booking после успешного подтверждения. Изменение цены в каталоге не переписывает уже существующие подтверждённые записи. Если quote устарел между просмотром и commit, API должен явно сообщить клиенту об изменении и получить подтверждение обновлённой цены, а не молча согласиться на другую сумму.
- Разрешения на изменение цен ограничены Organization и Location по RoleAssignments; нельзя применить override чужой организации. Скидки, индивидуальная стоимость мастера, налоги/валюта и расчёты — самостоятельные решения.
- Длительность услуги не меняется при филиальном price override, а отдельный post-service buffer относится к занятости мастера, не к цене услуги.

## Длительность Service (ACCEPTED F1/F2, DEC-049)
- Каждая Service имеет одну duration, используемую для любых мастеров/филиалов организации; нет staff/location-specific overrides. Для другого временного варианта требуется отдельная Service.
- Клиентский интервал записи рассчитывается от начала по duration выбранной Service; дальнейшая занятость мастера может включать только согласованный post-service buffer, **не** буфер до услуги и не дорожный буфер.
- **PROPOSED implementation:** сохранять duration snapshot и связанный post-buffer snapshot у Booking, чтобы изменение каталога не меняло существующие активные визиты и не создавало незаметных конфликтов. Конкретные поля/обработка обновления каталога требуют контрактного ревью.

## Мультифилиальные инварианты (ACCEPTED для F2)
- Organization владеет общей CRM Customer, но каждая Booking принадлежит конкретной Location; слоты рассчитываются с учётом её рабочих часов, адреса, мастеров и доступных услуг.
- **ACCEPTED F2:** один StaffProfile может иметь несколько StaffLocationAssignments в разных Locations одной Organization. Ресурсный ключ проверки активных броней — (tenantId, staffId, timeRange), **без locationId как части ключа**, чтобы два филиала не могли забронировать мастера на пересекающееся время.
- Доступ к брони проверяется по tenantId и authorization scope филиала. Записи других филиалов нельзя читать только по известному bookingId.
- Отчёты можно группировать по организации и филиалу; числовые лимиты филиалов — тарифное решение, не schema constraint.

## Multi-location Staff Scheduling (ACCEPTED продуктовый инвариант, детали реализации PROPOSED)
- Хранить единую запись StaffProfile организации и отдельные привязки к филиалам. Не создавать копию мастера на каждый адрес.
- Availability конкретного филиала = его локальные смены/назначения услуг ∩ общая незанятость мастера по **всем** филиалам; при записи и переносе пересчитывать и проверять инвариант в одной атомарной операции.
- Перекрывающиеся смены одного мастера в нескольких филиалах также должны иметь явную политику: нельзя выдавать одновременно доступные слоты в двух локациях без проверки занятости и реальной выполнимости.
- Изменение графика, смена филиального назначения и перенос записи не должны незаметно сделать действующие брони конфликтными.
- **ACCEPTED F1/F2:** алгоритм доступности не рассчитывает время дороги между филиалами, не вводит travel buffer и не проверяет возможность физического перемещения. Администратор самостоятельно задаёт рабочие смены/перерывы с нужными промежутками. Непересекающиеся записи в разных филиалах допустимы, если они укладываются в назначенные смены. Проверка пересечений активных броней между филиалами обязательна.
- Проверить concurrent create в двух Locations по одному staffId, обработку DST разных location timezones, multi-location reschedule и staff access scope.

## Настраиваемый буфер после услуги (DEC-047, 2026-11-14)
**ACCEPTED:** мастер недоступен для следующей клиентской брони в течение указанного в Service необязательного времени **после** фактического завершения услуги; до начала услуги автоматический дополнительный интервал не создаётся. Это не дорожный буфер (DEC-042).

**PROPOSED:** у Booking отдельно хранятся клиентский `startAt/endAt` и занятость ресурса через `occupiedUntil` либо post-buffer snapshot. Проверка недопущения overlap использует `[startAt, occupiedUntil)`, в том числе между разными филиалами одного StaffProfile. Буфер не искажает цену, время услуги для клиента и не образует дополнительный Visit. Значение по умолчанию 0, применённый buffer фиксируется snapshot. Вопрос работы буфера за пределами смены и изменения настройки для уже созданных броней — на review.

## Предлагаемая стратегия
Транзакции PostgreSQL и DB-level проверка пересечения временных диапазонов (возможный exclusion constraint на tstzrange, btree_gist), дополненная синхронизацией операций booking/change-schedule. Оформить ADR и stress/concurrency spike. Не полагаться только на проверку свободных окон в коде.

## Политики клиентской отмены и переноса (ACCEPTED продукт / PROPOSED алгоритм)
- В F2 Organization задаёт временные пределы самостоятельной отмены и переноса, с **переопределениями для отдельных Service**. Клиент управляет только своей подтверждённой бронью через авторизованный API.
- После клиентского дедлайна self-service команда возвращает запрет по политике и предлагает обратиться к администратору; сотрудник действует по отдельному разрешению и location scope.
- **Предлагаемый контракт:** отдельные cancelDeadline и rescheduleDeadline, вычисленные относительно startAt (UTC), серверная проверка на commit; timezone филиала — для отображения. Service override имеет приоритет над организационным default (требует детального согласования).
- **Предлагаемый инвариант:** CancelBooking атомарно освобождает интервал и сохраняет историю; RescheduleBooking атомарно получает новый слот и освобождает старый без временного удаления/отмены прежней брони. При ошибке старая Confirmed бронь остаётся.
- **Не утверждено:** изменения дедлайнов для уже созданных записей, точные дефолты, исключения по филиалу, возможности смены мастера/филиала при переносе, правила опозданий и предоплаты.

## Статусы (продуктовое решение ACCEPTED, технические переходы PROPOSED)
**ACCEPTED 2026-11-14:** при создании новой клиентской брони, если слот доступен и сервер успешно фиксирует операцию, статус сразу `Confirmed`, без согласования с администратором. Нет обычной `Pending`-заявки, которая удерживает слот; UI ждёт серверного commit перед показом успеха. Остальные статусы: CancelledByClient, CancelledByBusiness, Completed, NoShow (конкретные transitions/permissions на ревью). `Pending`/hold допускаются лишь как отдельно утверждённый flow с TTL/recovery.
После атомарного commit событие/уведомление через outbox не влияет на валидность брони при временной недоступности провайдера. История статусов сохраняется. Финансовая операция и закрытая бронь — разные сущности.

## Владение данными
Catalog владеет услугами, Staff — мастерами, Scheduling — исключениями/часами, Customers — контактами, Bookings — бронями и историей. Reporting строит агрегаты, не изменяя операционные данные. Чужие таблицы читают через публичные read ports.

## Commands/events
CreateBooking, RescheduleBooking, CancelBooking; booking.created, booking.rescheduled, booking.cancelled, visit.completed. Внешняя доставка через transactional outbox и idempotent consumers.

## Вопросы
Отсроченная оплата и слот hold, мультиуслуги, дополнительные ресурсы, отрезки по ночам, буферы между услугами (не путать с отклонёнными travel buffers), смена цены, overlapping staff across businesses, ручные брони админа, правила late cancellations.

## Тесты
Массовый параллелизм; перебои после commit; дубли event; отказ интеграции; отпуск после уже назначенных броней; чужой tenant; DST и границы суток.
