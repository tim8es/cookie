# ADR-0003 — Атомарное бронирование и согласованность графика

**Статус: PROPOSED** · Issue #11 · REQ-002,003,006.

## Решение на ревью
Один Bookings domain API для всех каналов, одни правила availability и booking. PostgreSQL фиксирует активные booking intervals транзакционно, с DB-level защитой от overlap (проверить exclusion constraint по tenant+staff+time-range, исключив отменённые состояния). Команды используют idempotency key, tenant context и контроль permission. Перенос — атомарное изменение старой/новой брони по согласованной статусной модели.

## Подтверждённая граница бронирования и рекомендации
**ACCEPTED от владельца:** одна запись — одна услуга (и выбранный исполнитель), следующий сервис проходит отдельное бронирование. Нет сложного multi-service пакета в одной атомарной операции на F1.
Связанные услуги и дополнительные предложения — отдельный configurable recommendations module (F2, предложенная реализация), вызывающий Catalog/Booking через публичные контракты, но не меняющий DB-инварианты одиночной брони.
**ACCEPTED:** F2 поддерживает несколько филиалов в одной организации; в F1 допустим один тестовый филиал с явным locationId. **ACCEPTED:** один StaffProfile работает в нескольких филиалах одной организации, активные бронирования защищены от пересечений вне зависимости от филиала. **ACCEPTED:** время перемещения между филиалами Cookie автоматически не учитывает (DEC-042). **Открыто:** специальные ресурсы и точная блокировка изменений графика. Одна запись по-прежнему содержит одного мастера.

## Автоматическое подтверждение клиентской записи (ACCEPTED 2026-11-14, DEC-043)
- F1/F2: при создании записи свободный слот **сразу подтверждается сервером** и сохраняется в статусе `Confirmed` в той же согласованной транзакционной операции. Отдельный шаг ручного одобрения администратором для обычной клиентской записи не нужен.
- `CreateBooking` проверяет актуальное расписание, длительность услуги, занятость мастера во всех филиалах, права клиента, idempotency key, цену/условия записи и атомарно фиксирует интервал. Если слот уже занят, возвращает доменный conflict и предлагает выбрать другое время; не создаёт `Pending`-заявку.
- UI показывает состояние обработки, но **не отображает успех до успешного ответа backend**. Успешный ответ содержит идентификатор и подтверждённый статус. Сбой Telegram/SMS/notification после commit не меняет `Confirmed` и не приводит к отмене записи; уведомление доставляется через outbox/job с повторами.
- `Pending` и временный hold **не нужны для стандартного потока создания брони**. Введение платежей/предоплаты или специализированных подтверждений позднее потребует отдельного ADR и строго описанных TTL/освобождения слота.
- Техническая стратегия транзакций и exclusion constraint остаётся PROPOSED до engineering spike; продуктовый инвариант отсутствия двойных броней ACCEPTED.

## Самостоятельная отмена и перенос с дедлайнами (ACCEPTED 2026-11-14, DEC-045)
- F2: владелец задаёт **настраиваемые временные ограничения для самостоятельной отмены и переноса** уже подтверждённых клиентских записей. Для отдельных услуг разрешены исключения (переопределения). Значения срока (например, 2/12/24 часа) — только примеры, не фиксированные правила Cookie.
- Дедлайны отмены и переноса могут быть разными; их диапазоны, значения по умолчанию и способы управления требуют UX/contract review. Основная политика организации и приоритет service override — **предлагаемая** модель. Филиальные переопределения отдельно не утверждены.
- До разрешённого дедлайна авторизованный клиент вправе отменить или перенести **свою** Confirmed бронь через любой канал, вызывающий единый Booking API. После дедлайна клиент не может изменить её самостоятельно: интерфейс предлагает обратиться к администратору. Это **не означает** автоматической отмены заявки и не вводит новый pending booking status.
- Администратор или другой уполномоченный сотрудник может обработать запрос позднее клиентского дедлайна в рамках своих scoped permissions; технические основания, уведомления и штрафы/возвраты — отдельные решения.
- **PROPOSED enforcement:** дедлайн вычисляется по моменту начала конкретной записи, сохранённому в UTC, и доверенному времени сервера; часовой пояс филиала используется для ввода/отображения. Проверка делается **в момент commit** команды, не по времени открытия страницы.
- **PROPOSED safety:** RescheduleBooking — атомарная замена интервала/времени с проверкой нового слота и права клиента; при конфликте старая Confirmed бронь сохраняется. CancelBooking меняет статус и освобождает ресурс атомарно, не удаляя историю. Idempotency/retry защищают от повторных операций.
- **Открыто:** применяется ли политика, действовавшая при создании брони, или текущая опубликованная политика при позднем изменении настроек салона; точные статусы и переходы, прерывания/начавшиеся услуги, допускается ли перенос в другой филиал и меняется ли цена.
- Не смешивать с финансовыми штрафами, предоплатой и возвратами: их отсутствие в этом решении не является разрешением или запретом этих механизмов.

## Отличия read vs write
Availability query может отобразить слот, потерявший доступность до подтверждения. CreateBooking проверяет ещё раз и возвращает domain conflict (409/BOOKING_CONFLICT) с возможностью обновить слоты.

## Единый ресурс мастера для всех филиалов (ACCEPTED F2)
- Одна сущность StaffProfile на Organization может быть назначена в несколько Locations. Каждая бронь хранит свой locationId, но **проверка пересечения активных визитов для staffId охватывает все Locations**, а не каждую по отдельности.
- PostgreSQL range exclusion или эквивалент должен обеспечивать уникальность по tenantId+staffId+overlapping time interval без включения locationId в exclusion key. Подтвердить конкретную схему constraint и статусы при DB design/spike.
- При вычислении слотов выбранного филиала исключать уже занятые интервалы этого мастера во всех филиалах. Concurrent booking в разных филиалах должен завершаться одной успешной бронью и доменной ошибкой для второго запроса.
- **ACCEPTED (DEC-042):** ни availability, ни Create/RescheduleBooking не рассчитывают дорогу и не добавляют travel buffers. Не блокировать последовательные непересекающиеся визиты в разных филиалах исключительно из-за физического расстояния: владелец/администратор сам разделяет смены с нужными интервалами. Это сохраняет риск слишком плотного вручную заданного расписания; обязательная атомарная проверка пересечений брони остаётся.

## Цена при выборе филиала (ACCEPTED продукт / PROPOSED контракт, 2026-11-14)
- **ACCEPTED:** у Service единый базовый прайс для Organization; выбранная Location может переопределить цену данной Service без изменения identity услуги, её длительности и без отдельного каталога.
- **PROPOSED:** QuoteServicePrice получает tenantId, locationId, serviceId и применяет точную филиальную цену либо базовую цену при отсутствии override. Клиент получает финальную цену выбранного филиала до подтверждения; CreateBooking повторно валидирует цену при атомарной операции.
- **ACCEPTED (DEC-055):** при CreateBooking используется **текущая** стоимость на сервере, независимо от ранее показанного Quote. При изменении цены **не возвращать PRICE_CHANGED и не требовать повторного согласия**. **PROPOSED:** в транзакции подтверждения фиксировать применённую цену/источник в Booking.PriceSnapshot, а в успешном ответе возвращать фактическую стоимость для отображения клиенту. Юридическая/UX-проверка прозрачности цены нужна до production.
- Ни допуск к записи, ни проверка отсутствия пересечений, ни единая длительность Service не зависят от того, какой филиальный price override выбран. Налоги остаются отдельным вопросом. Персональные цены мастеров приняты в DEC-053, а совместное применение скидок и промокодов — в DEC-057, см. разделы ниже.

## Индивидуальная цена для мастера в конкретном филиале (ACCEPTED продукт / PROPOSED resolver, 2026-11-14)
- **ACCEPTED:** F2 допускает своё значение цены одной Service для конкретного StaffProfile в конкретном Location. Это не меняет идентификатор Service, фиксированную Service.duration или её post-service buffer.
- Мастер с работой в двух филиалах не переносит индивидуальную цену из первого филиала во второй: настройки филиальные.
- **PROPOSED:** Quote учитывает tenantId/locationId/staffId/serviceId. Resolution: staff-location-service override → location-service override → Service.basePrice; применять только если мастер действительно оказывает услугу в филиале.
- **ACCEPTED (DEC-055):** CreateBooking рассчитывает действующую серверную стоимость выбранных Location+Staff+Service в момент подтверждения, **без сравнения с клиентским Quote для повторного согласия**. **PROPOSED:** защитить чтение действующих прайсов и фиксацию PriceSnapshot в согласованном транзакционном/версионном протоколе, вернуть применённую цену в ответе; точный DB/API контракт и race handling на ревью.
- Ценовые категории сотрудников как системный price tier не обязательны; скидки/налоги не являются частью решения DEC-053.

## Устаревший Quote и актуальная стоимость (ACCEPTED 2026-11-14, DEC-055)
- Клиент мог увидеть 1 500 ₽, но к моменту серверного CreateBooking действующая цена выросла до 1 700 ₽. В выбранной продуктовой политике бронь создаётся по **1 700 ₽**, если остальные проверки успешны; дополнительного запроса подтверждения новой цены нет.
- Веб, бот, AI и внешние каналы обязаны использовать одну серверную процедуру определения стоимости. Не доверять price из payload или ранее кешированному frontend state.
- **PROPOSED:** вернуть финальную сумму в ответе Confirmed и показать её клиенту на экране результата/в уведомлении. Не корректировать задним числом ранее подтверждённую бронь при будущих изменениях прайса.
- **Риск, требующий отдельного review перед коммерческим запуском:** неожиданное повышение стоимости создаёт клиентские претензии и потенциальные требования к раскрытию цены/согласию по применимому праву. DEC-055 отражает продуктовый выбор, **не является** юридическим заключением и не отменяет compliance gate.

## Совместимые скидки и промокоды (ACCEPTED продукт / PROPOSED реализация, DEC-057)
- В F2 одна Booking может получить несколько скидок и/или промокодов, **если владелец разрешил их сочетание**; несовместимые предложения не складываются автоматически. Отдельный paid add-on для этого решения не требуется.
- Начальная стоимость берётся из Catalog price resolver по Service+StaffProfile+Location; совместные скидки применяются после выбора этой стоимости, независимо от Service.duration и post-service buffer.
- **PROPOSED:** единый серверный discount/promotion evaluator для UI/Telegram/AI/Booking API. Перед commit повторить eligibility/compatibility и лимиты, обеспечить идемпотентность и защиту от двойного расходования ограниченных промокодов.
- **PROPOSED:** сохранить воспроизводимый breakdown базовой стоимости, применённых скидок и итоговой цены в Booking snapshot. Никаких доверенных вычислений только на frontend.
- **ACCEPTED DEC-059:** сначала вычесть фиксированные суммы, затем применять проценты последовательно к текущему остатку. Пример: 1 500 ₽ − 200 ₽ = 1 300 ₽, затем 10% → **1 170 ₽**. Следующая процентная скидка берёт базой 1 170 ₽, а не исходную цену.
- **ACCEPTED DEC-061:** финальный результат после всех совместимых скидок округляется **до целого рубля**, не до копеек. **ACCEPTED DEC-063:** на ровно 50 копейках применять half-even. **ACCEPTED DEC-064:** итог не ниже 0 ₽, избыточная часть скидки не применяется. **ACCEPTED DEC-066:** одноразовый код при частичной фактической скидке > 0 ₽ расходуется, при нулевой не расходуется. **ACCEPTED DEC-076:** внутри каждого типа автоматические скидки идут раньше промокодов. **ACCEPTED DEC-078:** внутри подгруппы приоритет задаёт владелец; **ACCEPTED DEC-080:** при равном заданном приоритете первой идёт большая потенциальная выгода. **ACCEPTED DEC-082:** равная выгода разрешается по ближайшему сроку окончания → дате создания → ID. **OPEN:** промежуточная точность, место standard priority и равные уровни в списке (DEC-088/090), лимиты, политика несовместимых предложений и глобальные квоты; отмена DEC-068, перенос DEC-070/072.
- DEC-055 остаётся в силе: CreateBooking применяет текущую цену и действующие скидки без повторного согласия на разницу с прежним Quote. Правовая проверка и показ клиенту итоговой суммы остаются необходимыми.

## Порядок применения скидок (ACCEPTED продукт / PROPOSED детали, DEC-059)
- Quote и CreateBooking после определения актуальной цены Service+Location+Staff и допустимых совместимых предложений применяют **все фиксированные денежные скидки первыми**, а затем процентные скидки **по очереди к текущему остатку**.
- `1500 - 200 = 1300`; `1300 × (1 - 0.10) = 1170`; следующая скидка 20% от 1 170 ₽ дала бы 936 ₽. Проценты **не** складываются в единый процент от исходной суммы.
- **PROPOSED:** сервер сохраняет шаги расчёта в breakdown и PriceSnapshot. Не доверять клиентскому порядку ввода/списку сумм как источнику разрешений или алгоритма.
- **ACCEPTED DEC-061:** финальная сумма в целых рублях. **PROPOSED:** точная decimal-арифметика без округления на каждом промежуточном шаге, однократное финальное округление. **ACCEPTED DEC-063:** half-even на ровно 50 копейках. **ACCEPTED DEC-064:** нижняя граница суммы 0 ₽. **OPEN:** сортировка внутри одинаковых типов, квоты, налоговый учёт. DEC-055 остаётся в силе.

## Финальное округление до целого рубля (ACCEPTED 2026-11-14, DEC-061)
- В вопросе №20 более поздний выбор владельца **В** заменил первоначальный **А**: финальная цена в Cookie F2 **в целых рублях**, без копеек.
- После исходной цены Service+Location+Staff и всех совместимых fixed/percentage скидок (DEC-059) сервер приводит финальную сумму к целому рублю. Quote, CreateBooking и уведомления применяют одну политику. DEC-055 (актуальная цена в момент создания брони) сохраняется.
- **PROPOSED:** использовать exact decimal без промежуточного округления до копеек и выполнять единственное финальное округление.
- **ACCEPTED DEC-063:** ровно 0,50 ₽ округляется к ближайшему чётному целому рублю по half-even; например 100,50→100 и 101,50→102. **ACCEPTED DEC-064:** нижняя граница цены 0 ₽; **OPEN:** внутренняя денежная точность и конкретный API contract. Не переносить данное округление автоматически на налоговые/фискальные расчёты.

## Банковское округление half-even (ACCEPTED DEC-063, 2026-11-14)
- Принят вариант Б вопроса №21: финальная цена после всех фиксированных и процентных скидок округляется к ближайшему рублю; при точном промежуточном результате `N + 0.50` выбирается ближайшее **чётное** целое N или N+1.
- Examples: `100.49 -> 100`, `100.50 -> 100`, `100.51 -> 101`, `101.50 -> 102`, `102.50 -> 102` (рубли). Отдельные скидки и промежуточные значения не обязательно округляются к рублю — exact decimal и единое финальное округление остаются **PROPOSED** (DEC-062).
- Единый алгоритм обязателен для Quote/Booking Engine/API/каналов и сохранения фактической финальной стоимости; контракт decimal/currency остаётся на ревью; отрицательные итоговые суммы запрещены DEC-064. Налоговое/фискальное округление этим ADR не определено.

## Нижняя граница итоговой стоимости 0 ₽ (ACCEPTED DEC-064, 2026-11-14)
- **Продуктовый инвариант:** для новой Booking после всех совместимых скидок итог не ниже нуля. 0 ₽ допустим, поэтому стандартная автоматическая запись Confirmed не требует отдельного ручного одобрения.
- Например, цена 500 ₽, совместимые фиксированные скидки 300 ₽ и 400 ₽. Суммарная максимальная скидка **500 ₽**, оставшиеся 200 ₽ номинала **не применяются** и не формируют баланс/выплату клиенту. Отнесение частичного вычета к конкретному промокоду требует отдельного решения.
- **PROPOSED:** сервер ограничивает величину фактически применяемого вычета текущим неотрицательным остатком; сохраняет номинал, фактически использованную и неиспользованную части в discount breakdown. После нулевого остатка дальнейшие процентные скидки не создают отрицательную цену.
- Даже бесплатная запись проверяет availability, permissions, tenant isolation и idempotency. Сумма 0 ₽ не даёт способа обойти ограничения расходования промокодов.
- **ACCEPTED DEC-066:** одноразовый промокод расходуется при любой фактически положительной скидке (включая частичную), не расходуется при нулевом эффекте. **ACCEPTED:** отмена восстанавливает код по DEC-068, а перенос только даты/времени сохраняет тот же redemption по DEC-070. **ACCEPTED DEC-072:** смена услуги/мастера/филиала возможна только через CancelBooking + новый CreateBooking. **ACCEPTED:** порог 1 ₽ до округления — DEC-074; автоматические скидки раньше промокодов внутри типа — DEC-076. **ACCEPTED DEC-078:** сортировка нескольких предложений одной подгруппы по приоритету владельца; **ACCEPTED DEC-080:** равные priorities разрешаются большей потенциальной выгодой; **ACCEPTED DEC-082:** равная выгода разрешается по expiry → createdAt → ID; **OPEN:** модель snapshot; направление сортировки принято DEC-086. Финальное round-to-ruble half-even (DEC-061/063) и юридический review DEC-055 действуют.

## Redemption одноразовых промокодов (ACCEPTED 2026-11-14, DEC-066)
- Правило расходования: только при успешной Confirmed Booking и положительной **фактически применённой** скидке по одноразовому промокоду. **Частичная** экономия (например, код 400 ₽ уменьшил остаток 100 ₽ на 100 ₽) всё равно полностью расходует одно право использования. Если applied discount 0 ₽ — код не списывается.
- Не создавать redemption для просмотра Quote, ввода кода, неуспешной или конфликтующей брони. Плата 0 ₽ и успешная бронь сами по себе не доказывают, что именно этот промокод дал скидку.
- **PROPOSED:** атомарно связывать CreateBooking/PriceSnapshot/redemption внутри одной транзакции с tenant/customer scopes, idempotency и безопасным учётом глобальных/персональных лимитов; повтор и конкурентная запись не списывают право дважды.
- **ACCEPTED DEC-074:** вычеты < 1 ₽ до финального округления не применять и не расходовать код вне зависимости от изменения итоговой цены. При вычете ≥ 1 ₽ код расходуется по DEC-066, даже если округлённая цена совпадает. **OPEN:** очередность нескольких кодов в одной группе; отмена DEC-068, перенос времени DEC-070, смена других полей — DEC-072.
- Все каналы обязаны использовать единый Booking Engine/Promotion policy; никаких отдельных правил у Telegram/AI.

## Восстановление одноразового промокода при отмене (ACCEPTED 2026-11-14, DEC-068)
- Если Confirmed Booking расходовала одноразовый код по DEC-066, то при **успешном CancelBooking** право на использование **восстанавливается**. Отказанная/неуспешная отмена, повтор команды и не подтверждённая смена статуса не возвращают дополнительные права.
- **Тот же код и те же ограничения:** срок действия не продлевается, scope, eligibility и лимиты не ослабляются. Восстановленное право не делает истёкший код автоматически применимым.
- Отмена проходит server-side authorization и настраиваемые сроки (DEC-045). Это не автоматический возврат денег, скидочный баланс и не отмена ради переносимой записи.
- **PROPOSED:** в одной транзакции с CancelBooking освободить только redemption, связанный с данной Booking, и сохранить audit. Idempotency и concurrency guard исключают двойной возврат права; следующая попытка применения проходит свежую проверку срока/лимитов.
- **ACCEPTED DEC-070:** при time-only RescheduleBooking с той же Service+Staff+Location исходная стоимость и расход кода сохраняются; возврата/нового списания нет. **ACCEPTED DEC-072:** смена услуги/мастера/филиала — только отмена и новая запись. **OPEN:** no-show/завершённая услуга, глобальные квоты, предоплата и refunds. При ошибке переноса старая Confirmed Booking не меняется.

## Перенос времени без изменения цены или промокода (ACCEPTED 2026-11-14, DEC-070)
- **ACCEPTED F2:** успешный RescheduleBooking меняет только дату/время существующей Confirmed Booking, оставляя **serviceId, staffId, locationId** неизменными. Первоначальная итоговая стоимость и применённые скидки остаются такими, какими были при подтверждении.
- Уже использованный этой Booking одноразовый промокод остаётся использованным **на ту же запись**. Его не расходовать повторно, не восстанавливать и не проверять срок действия заново только из-за перемещения времени. Устаревший прайс и истёкшая акция не переоценивают записанную цену.
- Это отдельный сценарий от **новой** CreateBooking по DEC-055 и от **отмены** с восстановлением кода по DEC-068.
- Проверки cutoff переноса (DEC-045), авторизации, доступного слота и пересечений мастера в нескольких филиалах остаются обязательными; неуспешный перенос оставляет старый слот, исходные деньги и promo redemption без изменений.
- **PROPOSED DEC-071:** атомарная смена занятости в рамках той же bookingId; сохранять PriceSnapshot и promoRedemption, аудитировать старый/новый slot; retries не создают вторую запись или второе использование кода.
- **ACCEPTED DEC-072:** смена услуги/мастера/филиала запрещена внутри RescheduleBooking; после отмены новая CreateBooking получает актуальные цены/скидки. **OPEN:** буфер/длительность при редактировании каталога, предоплата и refunds.

## Изменение услуги, мастера или филиала: отмена и новая запись (ACCEPTED DEC-072, 2026-11-14)
- Любое изменение `serviceId`, `staffId` или `locationId` нельзя оформить через RescheduleBooking. В F2 требуется **успешная CancelBooking прежней записи**, затем **отдельная CreateBooking** с новым bookingId; эти операции не являются атомарным обменом слотов.
- При отмене соблюдаются права и дедлайны (DEC-045); если отмена отклонена, прежняя Confirmed Booking сохраняется. Успешная отмена возвращает право на ранее использованный одноразовый промокод по DEC-068, **не продлевая срок его действия**.
- Новая CreateBooking проверяет новый слот, мастера, услугу, филиал и применимость скидок/промокодов заново, используя текущую серверную стоимость (DEC-055). Не копировать PriceSnapshot или redemption отменённой брони; уже истёкший промокод нельзя применить просто из-за восстановления права.
- Если CancelBooking успешна, но новый слот уже занят или создание отклонено, прежняя бронь **остаётся отменённой**. Не обещать клиенту сохранение старого слота или гарантированную замену. Временной перенос DEC-070 остаётся отдельной операцией, сохраняющей исходные условия.
- **PROPOSED DEC-073:** отдельные команды, idempotency keys и audit, явный отказ при попытке менять serviceId/staffId/locationId в RescheduleBooking и предупреждение о рисках до CancelBooking. Детали UX, предоплаты и refunds остаются на ревью.

## Минимальный фактический вычет 1 ₽ (ACCEPTED 2026-11-14, DEC-074)
- Для каждой отдельной скидки взять **фактически применимый вычет** после ограничения неотрицательным остатком до финального round-to-ruble half-even. Если вычет менее 1 ₽, пропустить скидку, не менять остаток и не создавать одноразовое promo redemption; порог 1 ₽ включительный.
- Цена 100 ₽, предложенная скидка 0,40 ₽ → не применяется, цена 100 ₽, код сохранён. Вычет 0,90 ₽ также пропускается независимо от возможной разницы конечного округления.
- Если применимый вычет 1 ₽, successful Confirmed расходует код по DEC-066, даже когда итоговые цены с кодом и без него округляются одинаково; решение относится к **порогу до округления**, а не к сравнению финальных итогов.
- **PROPOSED DEC-075:** price cap, порог 1 ₽, применение или пропуск и аудит причины. **ACCEPTED DEC-076:** auto раньше promo внутри fixed и percent. **OPEN:** порядок внутри однотипных auto-предложений или внутри нескольких промокодов, взаимодействие нескольких малых скидок, точность арифметики, API и ledger.
- Это дополняет DEC-061/063 и не меняет DEC-055 для новой Booking, DEC-068 отмены, DEC-070/072 переноса.

## Автоматические скидки перед промокодами внутри типа (ACCEPTED DEC-076, 2026-11-14)
- **Принятый порядок:** фиксированные автоматические скидки → фиксированные промокоды → процентные автоматические скидки → процентные промокоды. Это одновременно соблюдает DEC-059 (фиксированные прежде процентных) и DEC-076 (автоматические прежде промокодов **в каждом типе**). Процентная автоматическая скидка не может обойти фиксированный промокод.
- К каждому предложению последовательно применять cap к текущему неотрицательному остатку (DEC-064), порог применимого вычета 1 ₽ до финального округления (DEC-074) и правило расходования одноразового кода на Confirmed (DEC-066). Пропущенное предложение не меняет остаток и не создаёт promo redemption.
- Пример: исходная сумма 500 ₽, совместимая фиксированная автоматическая скидка 500 ₽, фиксированный одноразовый промокод 400 ₽. Автоматика обнуляет цену, promo appliedDiscount=0 ₽, код сохранён. Если автоматическая скидка 300 ₽, код реально вычитает оставшиеся 200 ₽ и расходуется при успешной Confirmed.
- **PROPOSED DEC-077/079:** один серверный evaluator для Quote/CreateBooking обходит четыре фиксированные группы, внутри каждой использует owner priority (ACCEPTED DEC-078), сохраняет applied/skipped breakdown и не доверяет порядку параметров в client payload. **ACCEPTED DEC-080:** при равных заданных приоритетах выбирать большую выгоду; **ACCEPTED DEC-082:** равная выгода → ближайший expiry → createdAt → ID; **OPEN:** место стандартного priority в списке, равные уровни и внутреннее представление rank (DEC-088/090).
- **ACCEPTED DEC-078:** правила внутри одинаковой подгруппы устанавливаются через priority владельца. **ACCEPTED DEC-080:** равные заданные priorities — сортировка по максимальной выгоде; **ACCEPTED DEC-082:** совпавшая выгода → ближайший срок окончания → созданная дата → ID; **OPEN:** расположение default и равные уровни в списке (DEC-088/090), лимиты, совместимость и decimal/ledger/API контракт; проверить эти вопросы до разработки.

## Приоритет владельца внутри подгруппы скидок (ACCEPTED product DEC-078, 2026-11-14)
- Владелец задаёт порядок применения предложений в пределах фиксированных автоматических, фиксированных промокодов, процентных автоматических и процентных промокодов **по отдельности**. Строгая очередность четырёх подгрупп, установленная DEC-059/076, не меняется.
- Пример внутри fixed:promo: остаток 500 ₽, совместимые коды номиналами 500 ₽ и 400 ₽. Если первым идёт код на 500 ₽, другой не применяется/не списывается; если первым идёт код на 400 ₽, второй даёт оставшиеся 100 ₽ и оба списываются после Confirmed (DEC-066). Оба варианта приоритетов допустимы, при равных приоритетах сначала идёт код с большей потенциальной выгодой (DEC-080); при совпадении самой выгоды действует DEC-082: ближайший срок окончания → дата создания → ID.
- **PROPOSED DEC-079:** backend сортирует правила по priority на стороне организации, сохраняет порядок и actual discount usage в PriceSnapshot, одинаково рассчитывает Quote и CreateBooking и проверяет права изменения. Не определять приоритет через порядок кодов в payload. Изменение настроек не пересчитывает ранее Confirmed Bookings; time-only перенос сохраняет цену по DEC-070.
- **ACCEPTED DEC-080:** одинаковые заданные priorities разрешаются сравнением потенциальной денежной выгоды (большая первая). **ACCEPTED DEC-082:** равная выгода → expiry → createdAt → ID; **OPEN:** расположение default и равные уровни в списке (DEC-088/090), data type шкалы, права делегирования, audit и конкурентные изменения. Сохранить tenant isolation.

## Одинаковые приоритеты: максимальная потенциальная выгода (ACCEPTED DEC-080, 2026-11-14)
- Внутри **одной** из четырёх подгрупп с равным owner priority скидка с большей денежной выгодой на текущем остатке оценивается первой. Сравнение не меняет фиксированный порядок подгрупп и не перескакивает через предложение с более высоким owner priority.
- Fixed:promo, остаток 500 ₽; два совместимых одноразовых кода на 500 ₽ и 400 ₽ имеют одинаковый priority. По DEC-080 сначала идёт код на 500 ₽, и код на 400 ₽ даёт 0 ₽, остаётся неиспользованным (DEC-066/074). Обе коды не должны расходоваться из-за одной лишь eligibility.
- **PROPOSED DEC-081:** вычислять потенциальный applied discount для текущего остатка до финального рублёвого округления с учётом cap 0 ₽ и порога 1 ₽. Уточнить пересчёт потенциальной выгоды после каждого применённого правила и точность/формат суммы до кода.
- **ACCEPTED DEC-082:** равенство выгоды разрешается expiry → createdAt → ID; **OPEN:** расположение default и равные уровни в списке (DEC-088/090), глобальные лимиты/eligibility и полный comparator. Не использовать client payload ordering как запасной comparator.

## Одинаковая выгода: ближайший срок окончания → дата создания → ID (ACCEPTED DEC-082, 2026-11-14)
- В пределах **одной** подгруппы при одинаковом owner priority и одинаковой потенциальной выгоде (DEC-078/080) применять сначала предложение с **ближайшим окончанием срока действия**. Если срок окончания совпал — сортировать по дате создания, затем по стабильному ID.
- **PROPOSED DEC-083:** сравнивать endAt по UTC instant ASC, затем createdAt ASC (более ранняя дата первой), затем ID ASC. Направления `createdAt ASC` и `ID ASC` утверждены DEC-086; реализация и аудит остаются PROPOSED.
- Пример: два совместимых одноразовых промокода по 300 ₽ с одинаковым приоритетом на остаток 500 ₽; один истекает 16 ноября, другой 20 ноября. Сначала применяется истекающий 16 ноября (300 ₽), затем второй частично (200 ₽); после Confirmed оба использованы (DEC-066), при успешной записи.
- **OPEN:** расположение default и равные уровни в списке (DEC-088/090), точность timestamp и формат уникального stable ID; направление принято DEC-086. Нельзя полагаться на порядок элементов клиентского payload. Snapshot существующих Confirmed и time-only перенос не пересчитывать.

## Tie-break срочных и бессрочных предложений (ACCEPTED DEC-084 / PROPOSED DEC-085)
- **ACCEPTED Q32 А:** внутри одной подгруппы при одинаковых owner priority и применимой денежной выгоде срочное предложение сортируется раньше бессрочного; среди срочных первым идёт ближайшее окончание (DEC-082). Если оба предложения без конца действия или expiry одинаковый, сравнить дату создания, затем стабильный ID; их направление — отдельный OPEN.
- **PROPOSED:** `endAt=NULL` означает отсутствие срока и сортируется после конечных сроков (`NULLS LAST`) только на этапе expiry. Истёкшие скидки не попадают в набор eligible. Quote и CreateBooking одинаковы, сохраняют idempotency, snapshot и атомарность расходования.
- **Контроль:** при цене 500 ₽ и двух совместимых одноразовых fixed:promo по 500 ₽ с равным priority сначала срочный (например, до 20 ноября), бессрочный не применяется и не расходуется; при смене срока уже Confirmed Booking не пересчитывать.
- **OPEN:** место default в списке и представление равных уровней, точные типы timestamp и audit/ledger; без автоматического решения этих вопросов.

## Завершающие ключи детерминированной сортировки (ACCEPTED DEC-086 / REQ-053)
- **ACCEPTED Q33 А:** при совпадении всех старших ключей (подгруппа, priority, потенциальная выгода и конец срока, включая оба `NULL`) сначала применить предложение с меньшим `createdAt` (`ASC`, ранее созданное), затем с меньшим стабильным ID (`ASC`).
- **Полный логический порядок:** fixed:auto → fixed:promo → percent:auto → percent:promo; затем owner priority; benefit DESC; действующий `endAt ASC` перед `NULL` (DEC-082/084); `createdAt ASC`; `ID ASC`. Отсутствие owner priority и направление его шкалы ещё OPEN.
- **Проверки:** два действующих promo с одинаковыми expiry/benefit/priority — более ранний createdAt первый; одинаковый createdAt — меньшее стабильное ID первое; два бессрочных — тот же fallback. Проверять одинаковость Quote/CreateBooking, отсутствие зависимости от input order, применимость/истечение, 0 ₽ floor, 1 ₽ min, атомарное redemption и неизменность существующих Confirmed/time-only Reschedule.
- **PROPOSED DEC-087:** контракт stable comparator и audit; конкретные типы ID/timestamp и обработка concurrency остаются на F0 review.

## Автоматическое назначение стандартного уровня приоритета (ACCEPTED DEC-088)
- **ACCEPTED Q34 В / REQ-054:** отсутствующий ввод владельцем приоритета скидки не блокирует её создание/активацию: система автоматически назначает **стандартный уровень**. Кампания на таком уровне конкурирует с кампанией, где владелец явно выбрал тот же уровень; ни «обязательно заполнить», ни «неуказанная всегда последняя» не допускаются.
- В общей серверной сортировке после четырёх неизменных подгрупп сравнивается effective priority, затем потенциальная денежная выгода DESC, действующий срок окончания ASC перед NULL, createdAt ASC, stable ID ASC. Quote/CreateBooking используют одинаковый resolver; исторические Confirmed и time-only Reschedule сохраняют прежнюю цену/redemption.
- **PROPOSED DEC-089:** явное разрешение effective priority на сервере и отображение назначенного уровня в Business Workspace, совместимый PriceSnapshot/audit. Конкретное место default в списке, группировка равных уровней, смена default и политика сохранения старого значения — OPEN.
- **Контрпример:** скидка без заданного приоритета и скидка с явно выбранным стандартным уровнем при равной выгоде/сроке сортируются по createdAt/ID (DEC-086), а не по признаку «был введён приоритет».

## Управление приоритетом без числового ввода (ACCEPTED DEC-090 / REQ-055)
- **ACCEPTED Q35 В:** владелец сортирует скидки/промокоды перетаскиванием в упорядоченном списке. Изменения разрешены только внутри соответствующей fixed:auto, fixed:promo, percent:auto или percent:promo подгруппы. Не менять системную очередность подгрупп (DEC-076) и серверные правила выбора при совпадении рангов.
- **PROPOSED DEC-091:** серверная команда reorder с tenant scope, RBAC, проверкой всех элементов, защитой от параллельного редактирования, версионированием и журналом действий; внутреннее поле ранга/группы допустимо, но UI не запрашивает ручной ввод чисел. Quote/CreateBooking используют согласованное effective priority и audit breakdown; исторические Confirmed и time-only Reschedule неизменны.
- **Инвариант:** более раннее место/уровень в пользовательском порядке применяется раньше более позднего **в пределах той же подгруппы**; если несколько предложений имеют один уровень, действует DEC-080/082/084/086. Как в UI создавать и переносить скидки с **одним приоритетом**, пока OPEN — простое присвоение всем уникальных позиций было бы несовместимо с уже принятыми tie-break.
- **OPEN:** механизм одинаковых рангов, расположение default level DEC-088, accessibility/mobile reorder, контракт и конфликтные обновления.

## Единая длительность услуги (ACCEPTED 2026-11-14, DEC-049)
- Длительность принадлежит Service в общем каталоге Organization и **одинакова для всех** StaffProfiles и Locations; staff-specific и location-specific duration overrides не вводятся в F1/F2.
- Если нужно другое время обслуживания, это отдельная Service (одна услуга в одной брони). При поиске слотов и Create/RescheduleBooking используется duration выбранной Service, затем отдельно добавляется разрешённый post-service buffer.
- **PROPOSED:** Booking хранит снимок длительности на момент подтверждения. Изменение Service duration не переносит автоматически завершение уже подтверждённых клиентских визитов. Точные условия изменения длительности и валидация старых записей на ревью.

## Буфер ПОСЛЕ услуги (ACCEPTED product / PROPOSED interval design, 2026-11-14)
- **ACCEPTED:** у каждой услуги может быть настраиваемое время недоступности мастера **после** завершения обслуживания. Буфер перед услугой **не требуется**, а travel buffer между филиалами не рассчитывается.
- Буфер не увеличивает длительность оказанной клиенту услуги, не должен смещать её клиентский endAt или создавать вторую самостоятельную бронь. Это дополнительная занятость мастера для Scheduling/Booking.
- **Предложенная модель:** `serviceStartAt`, `serviceEndAt`, `occupiedUntil = serviceEndAt + service.afterBufferMinutes`; конфликтную занятость проверяем по полуоткрытому диапазону `[serviceStartAt, occupiedUntil)`. Применяется независимо от филиала одного StaffProfile и к Create/RescheduleBooking.
- **Предложение:** 0 минут по умолчанию, настройка только на Service (без обязательных personal/location overrides). Сохранять фактически применённый post-buffer как snapshot у Booking, чтобы изменение каталога не переписало историю и не вызвало неявные конфликты действующих записей.
- **На ревью:** должен ли post-buffer полностью помещаться в рабочую смену, максимальное значение, UI отображение занятого интервала, миграция при изменении услуги и другие несвязанные service buffer сценарии. Конкретный PostgreSQL constraint остаётся PROPOSED.
- **Тест:** 10:00–11:00 клиентская услуга + 10 минут post-buffer делает 11:00–11:10 недоступным; 11:10 — потенциально доступно. Визит в другом филиале на 11:05 запрещён из-за пересечения занятости, но время дороги в расчёте не участвует.

## График и бронь
Добавление отпуска или сокращение смены при наличии визитов не может молча оставить противоречивые брони. Booking и Scheduling должны участвовать в синхронизированном протоколе изменения доступности (напр. staff/day lock и проверки внутри транзакции) или в одном консистентном агрегате. Конкретная стратегия выбирается после concurrency spike, а не по названию «модуль».

## Согласование и прямое изменение графика (ACCEPTED продуктовая политика, реализация PROPOSED)
- В F2 Owner может назначить сотруднику режим SELF_EDIT или APPROVAL_REQUIRED; проверка роли, tenant, филиала и права на изменение выполняется сервером.
- В режиме SELF_EDIT команда Scheduling изменяет график сразу **только при отсутствии неразрешённых конфликтов**. В APPROVAL_REQUIRED команда создаёт заявку, а подтверждение выполняет независимый уполномоченный actor.
- При подтверждении **повторно** проверить права, расписание и конфликтные брони внутри синхронизированного протокола Scheduling/Booking. Отказ/конфликт не меняет подтверждённую бронь и не оставляет противоречивый график.
- Минимальные статусы workflow: Pending, Approved, Rejected, Withdrawn, BlockedByConflict (черновик статусов, согласовывается при контрактном проектировании). Повторы command по idempotency key не создают дубли.
- Временные слоты, затронутые pending request, остаются доступными по текущему расписанию, если отдельно не принято решение о hold; UI не должен считать Pending уже применённым изменением.
- Любые действия через веб, Telegram и AI используют те же Scheduling commands и права. Запрет одобрения собственной заявки обычным staff — рекомендуемое безопасное правило на ревью.

## Время и статусы
UTC instants + IANA timezone, explicit service duration/buffer. **ACCEPTED:** обычная новая запись сразу создаётся как Confirmed; статуса ожидания ручного одобрения нет. Последующие статусы: CancelledByClient / CancelledByBusiness / Completed / NoShow (детали переходов PROPOSED). Hold/Pending возможны только в отдельном будущем сценарии с явно определённым TTL и восстановлением, не в стандартном F1/F2 create-flow.

## Не выбранные подходы
Клиентская блокировка слота; только in-memory mutex; отдельный scheduler microservice без гарантированной транзакции; AI прямой UPDATE booking.
