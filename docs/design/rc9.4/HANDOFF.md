# kuki — Design-to-code handoff RC9.4

**Статус:** визуальный кандидат для реализации; пользователь указал, что RC9.3 приближен к приемлемому результату. Это не разрешение на production rollout, новый scope F2 или окончательный Design Freeze. RC9.4 — очистка представления и спецификация переноса, а не готовый Svelte-патч.

2. `kuki-concept-rc9.4.html` — визуальный эталон, `kuki-components-rc9.4.html` — интерактивные примеры 32 контрактов. Оригинальный RC9.3 включён в `base-rc9.3/`. Синтетические числа, даты, справочные надписи и локальные обработчики **не являются требованиями** к production.
3. `COMPONENTS.md`, `token-reference.json` — карта переиспользования, геометрия и предлагаемые интерфейсные контракты. Они не являются утверждённым API DTO или автоматически применяемым CSS.
4. `docs/design/screen-registry.md` (#338) — существующие IDs B-01…B-21/C-01…C-12/X-01…X-05. Статусы SOURCE/LEGACY/PLANNED не означают PASS.
5. `docs/architecture/ADR-0005-shared-booking-ui.md` (ACCEPTED) — единый Booking UI, общие компоненты и адаптеры окружения. `docs/README.md` — индекс требований. При конфликте выполнить принятый контракт, описать визуальное отклонение и вынести только существенное продуктовое противоречие на review.

Проверено чтением текущего main: `AGENTS.md`, screen registry (blob `ad0c0fdab7b9f718737fd052869b89bc03da3e9e`), ADR-0005 (`8cfd29edc753ed13818872cc8fd7a213b9634f01`), `package.json` (`60d378b4e0c0ea8e2d33038f96f8c2487e1e3499`), `apps/web/src/styles/tokens.css` (`96ba6452fa1b815a2aed7bdcd7db3cdf1d0eb230`), `RealOwnerWorkspace.svelte` (`d8a27cdabba7acd35a31a7c30cbefa0e14f85e91`), `navigation.ts` (`c5e0ab24173b3559cba3b5e1c279f336e8c1821c`), `App.svelte` и списки каталогов. ## 2. Открытие и разделение представлений

Распакуйте архив и откройте `index.html` в обычном браузере. Ссылки открывают отдельные роли и каталог. По умолчанию `kuki-concept-rc9.4.html` — product view; `?review=1` включает демонстрационные инструменты (роль, сброс, искусственные ошибки, демонстрационный тариф, тестовый импорт/доставка). Для надёжной навигации используйте локальный статический сервер: `python -m http.server 8000` из папки пакета. Визуальный макет не подключён к API; не вводить реальные сведения. Прямые URL в этом окружении блокировались политикой Chromium, режимы проверены через `set_content` и явное переключение атрибута документа.

В продукт не переносить: DemoToolbar, DemoFooter/Notices/State, фикстуры, тестовые роле-переключатели, синтетические цены/даты, условные mock OTP, кнопки имитации ошибок, учебный CSV, искусственные таймеры, сценарные отметки F1/F2/PROPOSED, комментарии об устройстве прототипа. QA-состояния — в изолированном каталоге / fixture harness, не в обычных маршрутах. Не удалять реальные подсказки, правовые условия, отсутствие доступа, уведомления об ошибках, подтверждение действий; не превращать недоступную функцию в обещание. RC9.4 скрывает строго перечисленные demo controls и исправляет выбранные строки, **оставляет** предупреждения о синтетических операциях (авторизация, согласия, подтверждение, публикация) и часть исторических учебных форм. `copy-audit.json` фиксирует точные замены. Это не исчерпывающая лингвистическая очистка всех диалогов.

## 3. Поддерживаемая реализация

Стек репозитория сохраняется: Svelte 5/Vite, TypeScript, pnpm, Node 26, PostgreSQL. Не копировать монолит HTML, цепочки переопределений render/act, CSS с каскадом исторических RC-версий, DOM post-processing и localStorage-реестры из концепта. Перенести визуальную структуру и состояния в реальные Svelte-компоненты с типизированными props/callbacks. Не подключать новый фреймворк. Сначала реестр и токены, затем общие компоненты, затем вертикальные рабочие сценарии. Один владелец изменений в общей UI-основе на итерацию.

- `apps/web/src/styles/tokens.css` уже существует; расширять его, сохраняя aliases shadcn (`--primary`, `--background`, `--ring` и т. д.). `styles/foundation.css`, `booking.css`, `calendar.css`, `owner-forms.css`, `responsive.css`, `appearance.css`, `feedback.css` и существующий `visual-system.css`: выявить перекрытия, заменить по мере миграции, не добавлять третий слой `!important`.
- `apps/web/src/lib/components/ui/` уже содержит `button`, `input`, `label`, `card`, `badge`, `dialog`, `separator`. Расширить существующее, не создавать дубликаты Button2, Select2 и т. п. Новые семейства — рядом с ними по соглашениям репозитория; составные элементы — `lib/ui/`. Конкретные имена новых файлов — предложенные, уточнить по актуальному main.
- Семантические токены: surface/ink/muted/border/primary/selected/focus/destructive, радиусы и размеры; не хардкодить по экранам. Публичная тема организации меняет только токены публичной оболочки; рабочий кабинет не перекрашивается. Публикация темы — через существующие валидированные API; черновик отдельно.
- Состояния `default`, `hover`, `focus-visible`, `pressed/selected`, `disabled`, `pending`, `error`, `empty` применяются по смыслу. Для формы сохранять ввод при recoverable failure, показывать сообщение у поля, не сбрасывать фокус. Для списка loading/empty/no matches/error разные. Кнопка pending защищает от повторного submit, не равна подтверждению.
- Использовать нативные DOM semantics, label/id, доступное имя, focus trap/restore в модальных диалогах, клавиатурную навигацию в меню, reduced motion. Не реализовывать доступность только цветом. Не добавлять собственный drag-scrollbar; `ScrollArea` — нативная прокрутка, единые токены, доступная зона и отсутствие вложенного скролла на мобильном.
- `PageHeader`: контекст организации, одно название раздела, глобальный поиск/филиал, вторичные действия, главное действие крайним справа. Контролы в одной строке 44 px; на узком экране перенос без overflow, главная кнопка сохраняет приоритет. Не возвращать аватар в шапку: `WorkspaceAccount` — существующая карточка организации; мобильное меню «Ещё». Не показывать главный action, если capability отсутствует; не создавать фиктивные кнопки ради симметрии. Меню не должны перекрываться карточками: top-layer или безопасный portal с position/flip/shift и max-height, Escape/outside click/focus restoration.

## 5. Интеграция с сервером: invariants

- Существующие `lib/api.ts`, `transport.ts`, `owner-reads.ts`, доменные `*-api.ts` — предпочитать их, не создавать параллельные providers. Список API путей и payload брать из актуальных contracts и тестов, не из прототипа. Никаких синтетических fallback в обычном режиме.
- Актор, членство tenant, филиал, capability и доступность модуля подтверждаются backend. Скрытие UI — удобство, не контроль безопасности. При отказе обновить доступ, не оставлять диалог с недоступными данными. Роль/филиал в URL не даёт полномочий.
- Booking: выбор услуги → филиал/мастер → время → проверка/контакты → подтверждение. Изменение выбора инвалидирует зависимые данные. Запрос availability / quote по фактическим данным. Цена окончательна после серверного подтверждения; изменения показать до безопасного повторного подтверждения по существующему контракту. Slot conflict возвращает к времени с сохранением контактов; retry при unknown result использует уже принятый idempotency/recovery. Не создавать второй визит. Success только после server commit; сбой уведомления не отменяет существующую запись.
- Политики отмены, переноса, графиков, буферов, тарифов и прочие настраиваемые параметры — tenant-owned, проверяемые и аудируемые сервером (#285); не фиксировать значения из макета. Half-even и другие ACCEPTED invariants не переносить в CSS или независимый JS-расчёт. Не публиковать F2/experimental по умолчанию.
- Нет разрешения на реальные ПДн, платежи, публичный пилот или production deploy. AGENTS.md требует #113/#165 до публичного Booking API, #175 отдельного согласования, #203, legal/restore gates. Изолированный local/private staging на синтетических тестовых данных.

## 6. Порядок PR и независимые агенты

1. **UI Foundation**: инвентаризация существующих примитивов/токенов и их потребителей, общая реализация PageHeader, Account, Button, Input, SelectMenu, ScrollArea, диалог и story harness. Согласовать публичные контракты с остальными агентами; отдельный PR. Не менять API. Удалить legacy только после миграции всех потребителей и регрессии.
2. **Workspace**: сначала B-20/B-03/B-04/B-05, затем справочники B-06–B-09, оформление B-10. Реальные данные/API, единые компоненты. Вертикальные независимые PR после foundation или stacked от его SHA.
3. **Booking**: общий layout/steps, picker, quote, recovery, confirmation и история. Не обходить fail-closed и F1 gates. Реальные owner/manual и public permissions не смешивать. Вначале реализовать поддержанный server-backed flow; заблокированные поверхности документировать. Отдельные PR по зависимостям, без fork UI.
4. **QA/reviewer**: независимое сравнение с reference, browser/keyboard/screenshot QA, тесты API/DB/role и архитектуры, evidence в PR. Не одобрять собственный PR. CI agent поддерживает существующий workflow и визуальные артефакты.

Каждый агент берёт Issue, фиксирует scope/ownership, проверяет активные PR, создаёт branch/worktree, не пушит main, не изменяет чужие файлы без координации. Не задавать владельцу вопросы о размерах, названиях, отступах или расположении, когда ответы есть в reference/contract. При реальном противоречии ACCEPTED/доступ/коммерция/право — отдельный review, продолжить независимые части.

## 7. Acceptance gates (предлагаемый критерий инженерного закрытия)

Для каждого screen ID заполнить: target screenshot, route, role/capability, компонентные IDs, actual API/contract, states, width, тест и результат, SHA, PR, отклонения. `SOURCE` не равно выполнено.

- Build/typecheck: `pnpm typecheck`, `pnpm typecheck:web`, `pnpm build:web`, `pnpm check:ui`, `pnpm check:boundaries`, `pnpm lint`, `pnpm format:check`, `pnpm test`; `pnpm test:integration` с настроенной DB и действующим CI. Проверить актуальные скрипты на ветке. `pnpm staging:local` — реальный runtime с миграциями; не считать demo:local доказательством staging.
- Visual: 320/375/768/1366/1440 px; light/dark публичной темы, длинные названия, много строк, no overflow, 44 px controls, popover top layer, focus, клавиатура, reduced motion. Снимки сравнить с RC9.4; объяснить intentional differences, не скрывать diff. Browser back/refresh/direct URL, мобильные safe areas, реальные Safari iOS/Telegram/third-party iframe для соответствующих surface gates.
- Functional: happy + loading + empty + error + forbidden + expired + unknown result; pending action; role/tenant isolation; module disabled from every entry; slot conflict, cancel/reschedule and idempotency; actual server commit and DB persistence after restart. Screenshot alone is not PASS.
- Architecture: один компонент/одна функция, одна тема и один слой tokens, нет per-screen override для базовых контролов, no new mock provider in real runtime. Новая вариация сначала через explicit variant; accessibility review. Каталог импортирует настоящий компонент, не воссоздаёт его HTML. Проверка реестра: каждый публичный shared component имеет story и usage; legacy вне реестра не считать закрытым.
- Final: independent review, exact PR SHA + CI evidence, checklist of untested items. Release/Design Freeze only after owner review and required gates; никаких автоматических коммерческих разрешений.
