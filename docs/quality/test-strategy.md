# Стратегия качества и верификации

**Статус: PROPOSED.** Следовать при начале coding, автоматизация тестов — задачи roadmap.

## Принцип
Нет «готово» без автоматически проверяемого поведения. Critical path: выбор услуги -> свободное время -> атомарная запись -> отображение во всех каналах -> перенос/отмена.

## Пирамида
- Unit: правила модуля, price quote, слоты, статусы, permissions.
- Contract: публичный interface/capability каждого модуля, adapters/error codes/schema version.
- Integration with real Postgres: миграции, транзакции, exclusions, idempotency/outbox.
- End-to-end Playwright: клиентский web/виджет/Mini App shell, кабинет, онбординг.
- Simulated provider tests: Telegram webhook, AI timeout/tool calls, map adapter errors.
- Security: tenant isolation, IDOR, CSRF/session, scope escalation.
- Load: concurrent booking and latency/connection saturation at measured profiles; no фантазийных SLA.

## Обязательные «сломать продукт» тесты
1. Два клиента одновременно выбирают один интервал.
2. Два разных канала одновременно отправляют одну idempotent command.
3. Администратор меняет график при занятых слотах.
4. Отказ Telegram/AI/карты после успешной записи не теряет бронирование.
5. Клиент одной организации пытается изменить данные другой.
6. Рестарт worker в момент отправки уведомлений не создаёт неконтролируемые дубли.
7. Миграция + rollback и восстановление бэкапа проходят в тестовом окружении.
8. Два клиента одновременно бронируют **одного мастера** на пересекающиеся интервалы в **разных филиалах**: успешна ровно одна бронь, другой запрос получает явный conflict; ключ ограничения не локален филиалу.
9. Перенос визита, изменение графика и перепривязка мастера к филиалу не создают пересечений активных бронирований и не удаляют историю. Проверьте доступы staff к данным клиентов только назначенных визитов.
10. Слоты одного мастера в филиале A корректно учитывают занятость филиала B и IANA timezone; **travel buffer не применяется** (ACCEPTED).
11. Два последовательных непересекающихся визита в разных филиалах разрешены при соответствующих сменах, даже если физически рядом нет времени на дорогу: Cookie не рассчитывает маршрут. Непосредственно пересекающиеся визиты по-прежнему отвергаются.

12. После успешного CreateBooking запись находится в статусе Confirmed сразу после commit и доступна администратору; в стандартном потоке нет ожидания одобрения.
13. Два конкурентных клиента пытаются занять один слот: один получает Confirmed, другой — явный conflict без Pending/двойной брони. Повтор одного idempotent CreateBooking не создаёт новую запись.
14. Отказ отправки Telegram/SMS/worker после commit не откатывает Confirmed; outbox повторяет уведомление без дублирования брони. UI не показывает «записан» до ответа сервера.

15. У клиентской самостоятельной отмены и переноса проверяются соответствующие настроенные дедлайны: до срока разрешено, после срока возвращается policy denial и предложение связаться с администратором; другой клиент не может изменять чужую бронь.
16. При исключении для отдельной услуги применяется правильная политика; её приоритет над общей настройкой тестируется после утверждения технического контракта. Изменение статуса/времени между просмотром UI и commit не обходит дедлайн.
17. Неудачный перенос (конкурентно занят новый слот, дедлайн прошёл, отказ прав) оставляет старую запись Confirmed и её интервал неповреждёнными. Успешная отмена освобождает слот атомарно; повторная команда идемпотентна.
18. Администратор обрабатывает поздний запрос только при соответствующих правах и филиальном scope; сроки и конфиденциальность соблюдаются во всех каналах, включая Telegram/AI.

19. После услуги 10:00–11:00 с post-buffer 10 минут нельзя записать того же мастера на 11:05 ни в одном филиале; с 11:10 слот может быть свободен, если позволяет график. Клиенту окончание услуги показывает 11:00, а не 11:10.
20. Буфер до услуги не добавляется; post-buffer 0 минут не меняет стандартную проверку занятости. Concurrent create/reschedule и изменение каталожного buffer не должны создавать скрытые конфликты; механизм snapshot утвердить до реализации.

21. Одна Service при бронировании у разных мастеров и в разных филиалах имеет одинаковое время клиентского обслуживания; в API нет неутверждённых staff/location duration overrides.
22. Две Service с разной длительностью корректно рассчитывают разные интервалы; post-service buffer добавляется только к занятости мастера. Изменение длительности в каталоге не должно молча менять время ранее подтверждённых визитов (механизм snapshot — на техническом ревью).

23. Одна Service с базовой ценой X доступна в двух филиалах: при явном override Y в филиале B Quote показывает Y только в B, а филиал A наследует X. Удаление override возвращает X, при этом Service ID и длительность не меняются.
24. Server-side Quote/CreateBooking не доверяет цене, которую передал клиент; неизвестная или чужая Organization/Location не позволяет читать/подменять филиальные цены. Цена 0 (если разрешена бизнес-правилами) должна отличаться от отсутствия override.
25. **ACCEPTED (DEC-055):** если Quote показал 1 500 ₽, а к моменту CreateBooking серверная цена стала 1 700 ₽, запись при успешном бронировании создаётся по **1 700 ₽ без повторного согласия**. Клиент получает фактическую сумму в подтверждении. Последующее изменение каталога не меняет уже зафиксированную Confirmed бронь (PriceSnapshot — PROPOSED implementation).
26. Комбинации скидок/промокодов по DEC-057 тестировать отдельно от исходных цен staff+location; порядок типов принят DEC-059, итог целыми рублями DEC-061, half-even на ровно .50 DEC-063. Открыты промежуточная точность и остальные границы. Индивидуальная цена мастера — не скидка.

27. При Service.basePrice=1 000 ₽ и Location override=1 200 ₽ мастер A без индивидуальной цены получает Quote 1 200 ₽, мастер B с индивидуальной ценой 1 500 ₽ — Quote 1 500 ₽. В другом филиале мастер B без индивидуального override наследует цену именно того филиала.
28. Изменение индивидуальной цены не меняет Service ID, длительность или post-service buffer. Удаление override возвращает наследование. Цена 0, если допустима, не тождественна отсутствующей настройке.
29. Нельзя выдать/изменить staff-location price для чужого tenant, не назначенного мастера или недоступной ему услуги; обычная staff роль не может повысить себе цену без отдельного permission.
30. Сайт/Telegram/AI и Booking API используют актуальную цену Location+Staff+Service. CreateBooking не принимает произвольную сумму от клиента; при price race применяется действующая серверная стоимость без повторного согласия (DEC-055). Точный транзакционный snapshot/response contract — на ревью.

31. Изменение прайса между quote и create: подтверждённая бронь использует свежую стоимость, цена из клиентского payload игнорируется; обычный PRICE_CHANGED/reconfirm flow отсутствует.
32. Успешный ответ Confirmed и последующие уведомления показывают фактическую сумму, принятую сервером; для неизменённой старой брони применяется её зафиксированная цена, не новый каталог.
33. Юридические и UX-требования раскрытия цены проверены до production: помечать риск несоответствия/жалоб, не считать DEC-055 подтверждением правовой допустимости.

34. В одной Booking допускаются автоматическая скидка и промокод (и несколько совместимых предложений), если их совместимость разрешена владельцем; несовместимые комбинации нельзя применять как единый набор.
35. Все каналы используют одинаковую серверную проверку скидок. Нельзя применить промокод чужой Organization или навязать серверу недействующую сумму через клиентский запрос.
36. При параллельном использовании лимитированного/одноразового промокода и повторе одной idempotent команды не допускается лишний расход квоты; возврат права после успешной отмены принят DEC-068; точный атомарный протокол, глобальные квоты и возврат денег — на ревью.
37. При смене прайса/скидок между Quote и CreateBooking действует актуальная серверная цена и eligible набор скидок (DEC-055); итоговая сумма и breakdown сохраняются в истории (модель snapshot PROPOSED).
38. **DEC-059/061 ACCEPTED:** сначала все фиксированные скидки, затем проценты последовательно к остатку, после всех скидок финальная сумма округляется **до целого рубля**. Для 1 500 ₽ − 200 ₽ − 10% ожидается 1 170 ₽ (не 1 150 ₽). ACCEPTED DEC-063: на X,50 ₽ half-even. ACCEPTED DEC-076: auto раньше promo в каждом типе. OPEN: порядок нескольких правил одной подгруппы, лимиты и промежуточная точность.

39. Две совместимые процентные скидки после фиксированной: 1 500 ₽ − 200 ₽ = 1 300 ₽; далее 10% → 1 170 ₽, далее 20% → 936 ₽ (расчёт процентов к текущему остатку, не к стартовой базе). Все каналы и серверный Quote/CreateBooking должны совпадать на этом примере.
40. Добавление фиксированной скидки не меняет порядок: она применяется **до** процентных скидок, независимо от последовательности выбора пользователем. Перестановка в payload не должна менять решение сервера. Финальная точность до рубля принята (DEC-061); half-even (DEC-063) принят; промежуточная точность и обработка вычетов больше оставшейся суммы остаются открытыми.

41. Финальная сумма после всех совместимых фиксированных и процентных скидок выражается **целым числом рублей**, без копеек, во всех каналах: Quote, CreateBooking/Confirmed, уведомления, история. Тест с 1 500 ₽, фиксированным −200 ₽ и −10% даёт 1 170 ₽.
42. **ACCEPTED DEC-063:** итоговое округление half-even к целому рублю: 100,49 → 100; 100,50 → 100; 100,51 → 101; 101,50 → 102; 102,50 → 102. Тестировать при финальной сумме после всех совместимых скидок (не на каждом шаге).
43. Проверить, что обновление прайса после ранее Confirmed Booking не пересчитывает сохранённую финальную цену, и что политика округления цены не применяется автоматически к отдельным налоговым/бухгалтерским суммам.

44. Сайт, Telegram, AI, Booking Quote и Confirmed CreateBooking одинаково применяют half-even к точной половине рубля. Проверить случаи чуть ниже/выше порога и повторную команду idempotency; история/price snapshot показывают фактически сохранённый итог.
45. Тестируемые денежные инварианты не применяют автоматически round-to-ruble к НДС/кассовым чекам, не утверждая невыбранные валютные/фискальные правила. Внутренняя precision policy ещё на F0 review; запрет отрицательных итогов и разрешение 0 ₽ утверждены DEC-064.

46. **DEC-064 ACCEPTED:** исходная цена 500 ₽, две разрешённые фиксированные скидки 300 ₽ и 400 ₽: итог 0 ₽, суммарный фактический вычет 500 ₽ и неиспользованный номинал 200 ₽. Никакой отрицательной цены, выплаты или кредитного остатка.
47. После достижения нуля последующие проценты не уменьшают сумму ниже нуля. Half-even и финал в целых рублях продолжают действовать; тестировать случаи 0 ₽, 0,49 ₽, 0,50 ₽ и 1,50 ₽ как готовые итоговые суммы.
48. Нулевая стоимость не обходит Booking concurrency, проверку свободного слота и Confirmed/idempotency; веб, Telegram, AI и Booking API возвращают один итог.
49. Для нескольких совместимых скидок сохранять проверяемые nominal/applied/unused в предлагаемом breakdown; очередность распределения частичных вычетов остаётся OPEN. **DEC-066:** одноразовый код расходуется при фактической скидке > 0 ₽, включая частичную, при 0 ₽ — нет. Атомарность и идемпотентность расходования проверить в тестах.

50. **DEC-066 ACCEPTED:** одноразовый код на 400 ₽ применился лишь на 100 ₽ к остатку цены — скидка > 0 ₽, запись Confirmed и право использования кода израсходовано. Код с applied discount 0 ₽ при Confirmed остаётся доступным.
51. Неуспешный CreateBooking (конфликт слота, rollback, validation) не тратит одноразовый промокод. Два concurrent CreateBooking/повтор одного idempotencyKey не могут дважды расходовать право использования или создавать невалидную бронь.
52. **ACCEPTED DEC-074:** фактически применимый вычет менее 1 ₽ до финального half-even не применяется, не уменьшает остаток и не расходует код независимо от гипотетического изменения округлённого итога. При вычете ≥ 1 ₽ код расходуется при Confirmed по DEC-066 даже если округлённая цена совпала.
53. Восстановление права на одноразовый код после успешной отмены принято DEC-068. При переносе только даты/времени без смены услуги, мастера, филиала скидка и redemption сохраняются (DEC-070). Другие виды переноса и распределение частичной скидки между несколькими однотипными кодами остаются OPEN.

54. **DEC-068 ACCEPTED:** после успешной CancelBooking, использовавшей одноразовый код с положительной скидкой, право на код восстановлено. Срок действия и scope не меняются. При истечении срока код остаётся неприменимым, даже если право восстановлено.
55. Запрещённая клиентская отмена после deadline, неуспешная попытка, чужой bookingId, rollback и отсутствие разрешения не восстанавливают код. Код с нулевой применённой скидкой не был списан — не создавать фиктивную restoration.
56. Два параллельных CancelBooking и повтор одной идемпотентной команды восстанавливают право **только один раз**. При concurrent CancelBooking/CreateBooking корректно учитываются ограничения и сохраняется связь redemption с booking.
57. Успешный CancelBooking не означает автоматически финансовый возврат или восстановление кредита. Перенос только времени сохраняет цену и промокод (DEC-070); смена услуги/мастера/филиала, no-show и глобальные квоты остаются отдельными решениями.

58. **DEC-070 ACCEPTED:** при смене только даты/времени в существующей Confirmed Booking (те же serviceId/staffId/locationId) сохраняются исходная конечная цена/price snapshot и использованный промокод, даже если текущая цена услуги выросла, скидочная кампания изменилась или код истёк.
59. Успешный time-only RescheduleBooking не создаёт новый promo redemption, не восстанавливает одноразовый код, не расходует второй раз и не меняет исходный breakdown скидок. Проверить idempotency/retry и несколько переносов подряд.
60. Ошибка RescheduleBooking из-за конфликта слота/дедлайна/прав оставляет старый Confirmed, старое время, цену и promo redemption; отдельно проверить cross-branch staff availability и post-buffer.
61. Цена актуального каталога при CreateBooking остаётся по DEC-055, но не должна подменять ранее зафиксированную цену при time-only RescheduleBooking (DEC-070). CancelBooking + новая CreateBooking не равны такому переносу и могут применить новые условия.
62. **DEC-072 ACCEPTED:** изменение serviceId/staffId/locationId через RescheduleBooking запрещено; требуются отдельные CancelBooking + новый CreateBooking с актуальными ценами/скидками. Ошибка такой попытки не изменяет старую бронь.

63. **DEC-072 ACCEPTED:** RescheduleBooking с попыткой поменять serviceId/staffId/locationId возвращает отказ без изменения Confirmed Booking, цены, промокода, слота и истории.
64. Если разрешённый CancelBooking успешно завершён, использованный одноразовый промокод восстанавливается по DEC-068, не продлеваясь; следующая CreateBooking получает отдельный bookingId, актуальную цену и скидки по DEC-055. Старые PriceSnapshot/Redemption автоматически не копируются.
65. Если CancelBooking запрещён по дедлайну или правам, прежняя запись сохраняется; **никакой обход через смену мастера/филиала/услуги**. Если CancelBooking успешен, но CreateBooking провалилась, старая остаётся Cancelled; нельзя обещать автоматическое восстановление или резервирование слота.
66. Concurrent попытка занять новый слот между CancelBooking и CreateBooking должна приводить к корректному отказу при создании; оба отдельных действия идемпотентны, история и status consistency сохраняются.
67. Client booking UI должен объяснять до отмены риск потери прежнего слота и пересчёт новой стоимости; смена только времени не попадает в этот сценарий и сохраняет условия по DEC-070.

68. **DEC-074 ACCEPTED:** исходная цена 100 ₽, скидка 0,40 ₽ → вычет не применяется, цена 100 ₽, одноразовый код сохраняется. Скидка 0,99 ₽ тоже пропускается независимо от влияния на конечное округление; 1,00 ₽ проходит порог.
69. Quote/CreateBooking, Web/Telegram/AI проверяют порог до финального half-even по фактическому вычету после cap; клиентский claimed appliedDiscount игнорируется. Даже скидка номиналом 10 ₽, ограниченная остатком 0,99 ₽, не применяется.
70. Пример 100,50 ₽ → 100 ₽ без скидки; вычет 1 ₽ → 99,50 ₽ → 100 ₽ по half-even. Хотя видимая итоговая цена совпала, применённый вычет 1 ₽ расходует одноразовый код при успешном Confirmed.
71. Пропущенная скидка не изменяет остаток для следующих совместимых предложений и не создаёт promo redemption. Аудит причины пропуска — PROPOSED.
72. **DEC-076 ACCEPTED:** четыре подгруппы фиксированы. **DEC-078 ACCEPTED:** владелец определяет порядок нескольких auto или promo внутри каждой подгруппы. **ACCEPTED DEC-080:** одинаковый priority разрешается большей потенциальной выгодой; **ACCEPTED DEC-082:** одинаковая выгода → ближайшее окончание → дата создания → ID; **OPEN:** отсутствующий priority, конкурирующие малые вычеты; не использовать произвольный tie-break по умолчанию.

73. **DEC-076 ACCEPTED:** последовательность любых совместимых скидок соблюдает четыре группы: fixed-auto → fixed-promo → percent-auto → percent-promo. Действия UI/порядок массива promoCodes не меняют выбранную сервером очередность групп.
74. Цена 500 ₽, fixed automatic −500 ₽, fixed one-use promo −400 ₽: итог 0 ₽; promo appliedDiscount=0 ₽, право использования сохранено при успешной Confirmed Booking.
75. Цена 500 ₽, fixed automatic −300 ₽, fixed one-use promo −400 ₽: promo actuallyApplied=200 ₽, итог 0 ₽; право расходуется по DEC-066 после успешной Confirmed Booking, излишний номинал не превращается в баланс.
76. Смешанный пример: 1000 ₽, fixed-auto 100 ₽, fixed-promo 200 ₽, percent-auto 10%, percent-promo 20% → последовательные остатки 900, 700, 630, 504 ₽. Каждый тип и канал должны совпадать.
77. Приоритизация внутри фиксированного или процентного типа не изменяет DEC-074: если после более ранней автоматической скидки промокод даёт фактический вычет меньше 1 ₽, его не применять и не расходовать независимо от гипотетического влияния на half-even.
78. **DEC-078 ACCEPTED:** owner priority задаёт сортировку нескольких auto-скидок одного типа и нескольких промокодов одного типа. При равных priorities большая потенциальная выгода утверждена DEC-080; одинаковая выгода разрешена DEC-082 через ближайший expiry → созданную дату → ID; OPEN: конкретный стандартный уровень и направление шкалы; сам default принят DEC-088.

79. **DEC-078 ACCEPTED:** в одной fixed:promo подгруппе при остатке 500 ₽ совместимые одноразовые коды 500 ₽ и 400 ₽. При owner priority 500-first: первый applied=500 ₽, второй applied=0 ₽, не расходуется. При owner priority 400-first: первый applied=400 ₽, второй applied=100 ₽; успешный Confirmed расходует оба. Смена порядка в клиентском payload не меняет приоритет.
80. Приоритеты владельца внутри подгруппы не меняют строгую очередность fixed:auto → fixed:promo → percent:auto → percent:promo. При priority у percent:promo выше priority у fixed:auto всё равно сначала fixed:auto.
81. Quote и CreateBooking используют одну tenant-scoped актуальную policy; изменения priority между показом Quote и CreateBooking не нарушают DEC-055 и сохраняют PriceSnapshot подтверждённой цены (snapshot PROPOSED). Time-only Reschedule сохраняет прежний результат по DEC-070.
82. **DEC-080 ACCEPTED:** равные заданные owner priorities разрешаются большей потенциальной выгодой **внутри** подгруппы, а не датой/ID/порядком payload. При одинаковой выгоде действует DEC-082: срок окончания → дата создания → ID. Неуказанный priority получает стандартный уровень по DEC-088; числовой default и направление шкалы на F0 review; отсутствие срока решено DEC-084.

83. **DEC-080 ACCEPTED:** fixed:promo с остатком 500 ₽, два совместимых одноразовых кода номиналами 500 ₽ / 400 ₽, равный owner priority → код 500 ₽ применяется первым и расходуется после Confirmed, второй код applied=0 ₽ и остаётся неиспользованным.
84. Контроль: если у кода 400 ₽ owner priority выше, чем у кода 500 ₽, сначала применяется 400 ₽, затем второй код на оставшиеся 100 ₽. DEC-078 сильнее tie-break DEC-080, оба кода считаются израсходованными после Confirmed.
85. Для процентных скидок одинакового приоритета сравнивать **потенциальный денежный вычет** на текущей базе, не только процентные числа без расчёта остатка; DEC-064 (cap) и DEC-074 (порог 1 ₽) остаются обязательными.
86. Проверить одинаковую сортировку/результат в Quote/CreateBooking, отсутствие влияния порядка promoCodes в payload и неизменность snapshot уже Confirmed при последующей смене owner priorities.
87. При равной потенциальной выгоде принят DEC-082: expiry ASC → дата создания → ID; числовой standard priority и точная реализация остаются OPEN/PROPOSED, без произвольной сортировки клиентским payload.

88. **DEC-082 ACCEPTED:** в fixed:promo два одноразовых предложения с одинаковым owner priority и потенциальной выгодой 300 ₽, оставшаяся стоимость 500 ₽. Первым применяется код, чей срок заканчивается раньше: 16 ноября перед 20 ноября (300 ₽ first, затем 200 ₽ applied second, оба расходуются при Confirmed).
89. При одинаковых expiry сервер сортирует по createdAt, затем по stable ID; проверить воспроизводимость Quote/CreateBooking и независимость от порядка кодов в payload. Направления приняты DEC-086: `createdAt ASC`, `ID ASC`; API/поле ID и audit требуют review.
90. Подгруппы, разные owner priorities и разная выгода имеют старшинство перед expiry: скидка с более ранним окончанием не может перескочить в другую подгруппу или обогнать более высокий priority.
91. Отсутствие явно указанного priority решено DEC-088 (автоматический стандартный уровень); числовая шкала ещё на ревью. Для бессрочных скидок принято DEC-084 — после срочных при равных остальных условиях; без fallback по клиентскому порядку.

92. **DEC-084 / REQ-052 ACCEPTED:** при равных owner priority и potential monetary benefit срочный промокод с действующим `endAt` выбирается раньше бессрочного с `endAt=NULL`. Цена 500 ₽; два совместимых одноразовых fixed:promo по 500 ₽, срочный до 20 ноября и бессрочный: применяется срочный, бессрочный не расходуется.
93. Два срочных предложения с равными priority/benefit: ближайший `endAt` первым (DEC-082). Два бессрочных: переход к createdAt, затем ID; сортировать по `createdAt ASC`, затем `ID ASC` по DEC-086.
94. Истёкший срочный промокод не побеждает бессрочный: expiry eligibility проверяется до tie-break. Перестановка promoCodes в payload не меняет результат Quote/CreateBooking. Уже Confirmed и time-only Reschedule сохраняют historical price/redemption по DEC-070.

95. **DEC-086 / REQ-053 ACCEPTED:** при равных owner priority и potential monetary benefit, одинаковых действующих expiry и разных createdAt из двух совместимых одноразовых fixed:promo номиналом 500 ₽ при остатке 500 ₽ выбирается более ранний `createdAt` (`ASC`); другой код остаётся неиспользованным. Повторить для двух `endAt=NULL` (DEC-084).
96. При одинаковом expiry и `createdAt` меньший стабильный ID применяется первым (`ID ASC`). Перестановка promoCodes в клиентском payload, различие порядка запросов к БД и каналов (web/Telegram/AI) не меняет Quote/CreateBooking и состояние redemption.
97. **Регрессия старшинства:** меньший createdAt или ID не должен обгонять другую скидку из более ранней подгруппы, большего owner priority или с большей денежной выгодой; действующий finite expiry всегда раньше NULL при равенстве предыдущих ключей. Истёкшие/недопустимые предложения не проходят eligibility. Не пересчитывать подтверждённые или перенесённые только по времени брони.

98. **DEC-088 / REQ-054 ACCEPTED:** владелец создаёт/активирует скидку без ручного выбора priority — операция допустима, Cookie назначает **стандартный уровень**. Другая скидка с явно выбранным тем же уровнем должна при равной выгоде проходить последующие tie-break DEC-082/084/086, без преимущества/штрафа за способ назначения.
99. Проверить, что неуказанное поле приоритета не трактуется как «самый низкий приоритет» либо validation error. При двух скидках одной подгруппы сравнивать standard и вручную заданный другие уровни в порядке будущей принятой шкалы (точный порядок — OPEN до Q35).
100. Quote/CreateBooking должны согласованно использовать effective priority для одной и той же версии настроек Organization; исторические Confirmed и time-only Reschedule не пересчитывать. **PROPOSED DEC-089:** storage/default inheritance, audit и UI. Не зафиксировать числовое значение/направление шкалы автоматически без владельца.

## Инженерный definition of done
- PR с привязанным Issue, тест-планом и документацией.
- Типизация, линтер, unit/contract/integration tests проходят в CI.
- Новое публичное capability описано контрактом, error policy и version.
- Нет прямого импорта внутренних файлов чужого модуля или чужого SQL.
- Новая операция с ПДн имеет permissions, аудит и retention правила.
- Изменение схемы сопровождается миграцией и сценарием восстановления.
- Изменения UI проверены на мобильном экране и desktop.
- Если у модуля нет документации или теста отключения, он не готов.

## Gate документации перед coding
REQ подтверждены, ADR ключевых tradeoffs решены или помечены как unblockable; декомпозиция с критериями приёмки, CI-план и risk register просмотрены; PR с документацией review/merge. После этого отдельно стартовать код.
