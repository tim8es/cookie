# Стратегия качества и верификации

**Статус: PROPOSED.** Следовать при начале coding, автоматизация тестов — задачи roadmap.

## Принцип
Нет «готово» без автоматически проверяемого поведения. Critical path: выбор услуги -> свободное время -> атомарная запись -> отображение во всех каналах -> перенос/отмена.

## Пирамида
- Unit: правила модуля, price quote, слоты, статусы, permissions.
- Contract: публичный interface/capability каждого модуля, adapters/error codes/schema version.
- Integration with real Postgres: миграции, транзакции, exclusions, idempotency/outbox.
- End-to-end Playwright: клиентский web/виджет/Mini App shell, кабинет, онбординг.
- Simulated provider tests: Telegram webhook, AI timeout/tool calls, map adapter errors.
- Security: tenant isolation, IDOR, CSRF/session, scope escalation.
- Load: concurrent booking and latency/connection saturation at measured profiles; no фантазийных SLA.

## Обязательные «сломать продукт» тесты
1. Два клиента одновременно выбирают один интервал.
2. Два разных канала одновременно отправляют одну idempotent command.
3. Администратор меняет график при занятых слотах.
4. Отказ Telegram/AI/карты после успешной записи не теряет бронирование.
5. Клиент одной организации пытается изменить данные другой.
6. Рестарт worker в момент отправки уведомлений не создаёт неконтролируемые дубли.
7. Миграция + rollback и восстановление бэкапа проходят в тестовом окружении.
8. Два клиента одновременно бронируют **одного мастера** на пересекающиеся интервалы в **разных филиалах**: успешна ровно одна бронь, другой запрос получает явный conflict; ключ ограничения не локален филиалу.
9. Перенос визита, изменение графика и перепривязка мастера к филиалу не создают пересечений активных бронирований и не удаляют историю. Проверьте доступы staff к данным клиентов только назначенных визитов.
10. Слоты одного мастера в филиале A корректно учитывают занятость филиала B и IANA timezone; **travel buffer не применяется** (ACCEPTED).
11. Два последовательных непересекающихся визита в разных филиалах разрешены при соответствующих сменах, даже если физически рядом нет времени на дорогу: Cookie не рассчитывает маршрут. Непосредственно пересекающиеся визиты по-прежнему отвергаются.

12. После успешного CreateBooking запись находится в статусе Confirmed сразу после commit и доступна администратору; в стандартном потоке нет ожидания одобрения.
13. Два конкурентных клиента пытаются занять один слот: один получает Confirmed, другой — явный conflict без Pending/двойной брони. Повтор одного idempotent CreateBooking не создаёт новую запись.
14. Отказ отправки Telegram/SMS/worker после commit не откатывает Confirmed; outbox повторяет уведомление без дублирования брони. UI не показывает «записан» до ответа сервера.

15. У клиентской самостоятельной отмены и переноса проверяются соответствующие настроенные дедлайны: до срока разрешено, после срока возвращается policy denial и предложение связаться с администратором; другой клиент не может изменять чужую бронь.
16. При исключении для отдельной услуги применяется правильная политика; её приоритет над общей настройкой тестируется после утверждения технического контракта. Изменение статуса/времени между просмотром UI и commit не обходит дедлайн.
17. Неудачный перенос (конкурентно занят новый слот, дедлайн прошёл, отказ прав) оставляет старую запись Confirmed и её интервал неповреждёнными. Успешная отмена освобождает слот атомарно; повторная команда идемпотентна.
18. Администратор обрабатывает поздний запрос только при соответствующих правах и филиальном scope; сроки и конфиденциальность соблюдаются во всех каналах, включая Telegram/AI.

19. После услуги 10:00–11:00 с post-buffer 10 минут нельзя записать того же мастера на 11:05 ни в одном филиале; с 11:10 слот может быть свободен, если позволяет график. Клиенту окончание услуги показывает 11:00, а не 11:10.
20. Буфер до услуги не добавляется; post-buffer 0 минут не меняет стандартную проверку занятости. Concurrent create/reschedule и изменение каталожного buffer не должны создавать скрытые конфликты; механизм snapshot утвердить до реализации.

21. Одна Service при бронировании у разных мастеров и в разных филиалах имеет одинаковое время клиентского обслуживания; в API нет неутверждённых staff/location duration overrides.
22. Две Service с разной длительностью корректно рассчитывают разные интервалы; post-service buffer добавляется только к занятости мастера. Изменение длительности в каталоге не должно молча менять время ранее подтверждённых визитов (механизм snapshot — на техническом ревью).

23. Одна Service с базовой ценой X доступна в двух филиалах: при явном override Y в филиале B Quote показывает Y только в B, а филиал A наследует X. Удаление override возвращает X, при этом Service ID и длительность не меняются.
24. Server-side Quote/CreateBooking не доверяет цене, которую передал клиент; неизвестная или чужая Organization/Location не позволяет читать/подменять филиальные цены. Цена 0 (если разрешена бизнес-правилами) должна отличаться от отсутствия override.
25. **ACCEPTED (DEC-055):** если Quote показал 1 500 ₽, а к моменту CreateBooking серверная цена стала 1 700 ₽, запись при успешном бронировании создаётся по **1 700 ₽ без повторного согласия**. Клиент получает фактическую сумму в подтверждении. Последующее изменение каталога не меняет уже зафиксированную Confirmed бронь (PriceSnapshot — PROPOSED implementation).
26. Комбинации скидок/промокодов по DEC-057 тестировать отдельно от исходных цен staff+location; порядок типов принят DEC-059, итог целыми рублями DEC-061, half-even на ровно .50 DEC-063. Открыты промежуточная точность и остальные границы. Индивидуальная цена мастера — не скидка.

27. При Service.basePrice=1 000 ₽ и Location override=1 200 ₽ мастер A без индивидуальной цены получает Quote 1 200 ₽, мастер B с индивидуальной ценой 1 500 ₽ — Quote 1 500 ₽. В другом филиале мастер B без индивидуального override наследует цену именно того филиала.
28. Изменение индивидуальной цены не меняет Service ID, длительность или post-service buffer. Удаление override возвращает наследование. Цена 0, если допустима, не тождественна отсутствующей настройке.
29. Нельзя выдать/изменить staff-location price для чужого tenant, не назначенного мастера или недоступной ему услуги; обычная staff роль не может повысить себе цену без отдельного permission.
30. Сайт/Telegram/AI и Booking API используют актуальную цену Location+Staff+Service. CreateBooking не принимает произвольную сумму от клиента; при price race применяется действующая серверная стоимость без повторного согласия (DEC-055). Точный транзакционный snapshot/response contract — на ревью.

31. Изменение прайса между quote и create: подтверждённая бронь использует свежую стоимость, цена из клиентского payload игнорируется; обычный PRICE_CHANGED/reconfirm flow отсутствует.
32. Успешный ответ Confirmed и последующие уведомления показывают фактическую сумму, принятую сервером; для неизменённой старой брони применяется её зафиксированная цена, не новый каталог.
33. Юридические и UX-требования раскрытия цены проверены до production: помечать риск несоответствия/жалоб, не считать DEC-055 подтверждением правовой допустимости.

34. В одной Booking допускаются автоматическая скидка и промокод (и несколько совместимых предложений), если их совместимость разрешена владельцем; несовместимые комбинации нельзя применять как единый набор.
35. Все каналы используют одинаковую серверную проверку скидок. Нельзя применить промокод чужой Organization или навязать серверу недействующую сумму через клиентский запрос.
36. При параллельном использовании лимитированного/одноразового промокода и повторе одной idempotent команды не допускается лишний расход квоты; правило возврата после отмены отдельно утверждается.
37. При смене прайса/скидок между Quote и CreateBooking действует актуальная серверная цена и eligible набор скидок (DEC-055); итоговая сумма и breakdown сохраняются в истории (модель snapshot PROPOSED).
38. **DEC-059/061 ACCEPTED:** сначала все фиксированные скидки, затем проценты последовательно к остатку, после всех скидок финальная сумма округляется **до целого рубля**. Для 1 500 ₽ − 200 ₽ − 10% ожидается 1 170 ₽ (не 1 150 ₽). ACCEPTED DEC-063: на X,50 ₽ half-even. OPEN: сортировка внутри групп, лимиты и промежуточная точность.

39. Две совместимые процентные скидки после фиксированной: 1 500 ₽ − 200 ₽ = 1 300 ₽; далее 10% → 1 170 ₽, далее 20% → 936 ₽ (расчёт процентов к текущему остатку, не к стартовой базе). Все каналы и серверный Quote/CreateBooking должны совпадать на этом примере.
40. Добавление фиксированной скидки не меняет порядок: она применяется **до** процентных скидок, независимо от последовательности выбора пользователем. Перестановка в payload не должна менять решение сервера. Финальная точность до рубля принята (DEC-061); half-even (DEC-063) принят; промежуточная точность и обработка вычетов больше оставшейся суммы остаются открытыми.

41. Финальная сумма после всех совместимых фиксированных и процентных скидок выражается **целым числом рублей**, без копеек, во всех каналах: Quote, CreateBooking/Confirmed, уведомления, история. Тест с 1 500 ₽, фиксированным −200 ₽ и −10% даёт 1 170 ₽.
42. **ACCEPTED DEC-063:** итоговое округление half-even к целому рублю: 100,49 → 100; 100,50 → 100; 100,51 → 101; 101,50 → 102; 102,50 → 102. Тестировать при финальной сумме после всех совместимых скидок (не на каждом шаге).
43. Проверить, что обновление прайса после ранее Confirmed Booking не пересчитывает сохранённую финальную цену, и что политика округления цены не применяется автоматически к отдельным налоговым/бухгалтерским суммам.

44. Сайт, Telegram, AI, Booking Quote и Confirmed CreateBooking одинаково применяют half-even к точной половине рубля. Проверить случаи чуть ниже/выше порога и повторную команду idempotency; история/price snapshot показывают фактически сохранённый итог.
45. Тестируемые денежные инварианты не применяют автоматически round-to-ruble к НДС/кассовым чекам, не утверждая невыбранные валютные/фискальные правила. Внутренняя precision policy ещё на F0 review; запрет отрицательных итогов и разрешение 0 ₽ утверждены DEC-064.

46. **DEC-064 ACCEPTED:** исходная цена 500 ₽, две разрешённые фиксированные скидки 300 ₽ и 400 ₽: итог 0 ₽, суммарный фактический вычет 500 ₽ и неиспользованный номинал 200 ₽. Никакой отрицательной цены, выплаты или кредитного остатка.
47. После достижения нуля последующие проценты не уменьшают сумму ниже нуля. Half-even и финал в целых рублях продолжают действовать; тестировать случаи 0 ₽, 0,49 ₽, 0,50 ₽ и 1,50 ₽ как готовые итоговые суммы.
48. Нулевая стоимость не обходит Booking concurrency, проверку свободного слота и Confirmed/idempotency; веб, Telegram, AI и Booking API возвращают один итог.
49. Для нескольких совместимых скидок сохранять проверяемые nominal/applied/unused в предлагаемом breakdown, но не утверждать очередность распределения частичного вычета и списание промокода до отдельного решения. Атомарность расходования лимитов тестировать после утверждения usage policy.

## Инженерный definition of done
- PR с привязанным Issue, тест-планом и документацией.
- Типизация, линтер, unit/contract/integration tests проходят в CI.
- Новое публичное capability описано контрактом, error policy и version.
- Нет прямого импорта внутренних файлов чужого модуля или чужого SQL.
- Новая операция с ПДн имеет permissions, аудит и retention правила.
- Изменение схемы сопровождается миграцией и сценарием восстановления.
- Изменения UI проверены на мобильном экране и desktop.
- Если у модуля нет документации или теста отключения, он не готов.

## Gate документации перед coding
REQ подтверждены, ADR ключевых tradeoffs решены или помечены как unblockable; декомпозиция с критериями приёмки, CI-план и risk register просмотрены; PR с документацией review/merge. После этого отдельно стартовать код.
