# Пользовательские сценарии / UX hypotheses

**Статус:** на ревью. Это проверяемые сценарии, не готовые макеты. У всех интерфейсов — одна предметная логика и правила доступа.

## Journey A — новый клиент на публичной странице
1. Открывает брендированную ссылку или виджет на сайте салона.
2. Видит услуги, цены, продолжительность, мастеров; может менять последовательность выбора услуги/мастера в интерфейсе, но валидирует комбинации через API.
3. Видит свободные интервалы минимум на 2 недели; выбирает день и слот.
4. Указывает минимальные контактные сведения, необходимые для записи, и предоставляет юридически необходимые согласия, если применимо.
5. Подтверждает бронь и получает ссылку для безопасного управления ею.
6. Может привязать Telegram для будущего быстрого входа; email необязателен.

**Важное:** анонимный доступ к управлению бронью возможен только по короткоживущей безопасной ссылке/верификации. Само знание ID записи недостаточно.

## Journey B — повторная запись
Клиент открывает «Мои записи», выбирает «Повторить» → прежняя услуга/мастер предзаполнены → выбирает доступную дату → подтверждает. Цена и длительность сверяются с актуальным каталогом, старые условия не подставляются молча.

## Journey C — клиент внутри Telegram
Бот принимает /start, показывает кнопки и открывает тот же Booking UI как Mini App. При чат-запросе бот отвечает на FAQ (адрес, график, оплата, подготовка к процедуре), предлагает услуги/слоты через единый booking API, проверяет идентичность пользователя, требует подтверждение на запись или перенос. В сложном случае передаёт обращение администратору с историей диалога в рамках разрешённого доступа. AI — отключаемая альтернатива сценарному пониманию, не отдельное хранилище бронирований.

## Journey B2 — рекомендации связанных услуг (отдельные брони)
Первая коммерческая версия не требует составного выбора нескольких услуг внутри одной брони: одна услуга и один мастер на запись. После успешной первой записи интерфейс может рекомендовать связанную услугу (например, уход после стрижки), настроенную салоном и доступную по отдельной лицензии.
- Клиент явно соглашается начать **новое бронирование**; часть выбора салона/услуги может быть предзаполнена.
- Новые дата/время/мастер проверяются в актуальном расписании и подтверждаются отдельно.
- Существующая бронь не отменяется, если подходящего слота для второй нет; не создаём ложную атомарную «корзину» услуг.
- F1 не требует рекомендательного движка, F2 допускает отдельный отключаемый модуль без AI.

## Journey C2 — выбор авторизации на сайте
На публичной странице пользователь выбирает телефон (с подтверждением владения для авторизации) или Telegram Login. В Telegram Mini App/боте использует Telegram identity без необходимости вводить телефон ради самой регистрации. При первой записи создаётся customer-profile конкретного салона. Данные Telegram/телефона связываются с учётной записью только после надёжной проверки, email необязателен.

## Journey D — сотрудник просит изменить график
Мастер заходит под ограниченной ролью, запрашивает выходной/смену часов, видит предварительные конфликты с бронями. Администратор подтверждает или отклоняет, конфликтные существующие записи требуют отдельного разрешения до применения. Сотрудник уведомлён о результате.

## Journey E — администратор в чате
Текстом (в будущем голосом) запрашивает «Что у меня на сегодня?»; авторизованная команда возвращает выборку только по разрешённой организации. Запрос «Перенеси запись ...» готовит предложение и требует подтверждения. Для неоднозначных клиентов и времён — уточнение, не угадывание.

## Journey F — владелец запускает салон
Онбординг: создаёт организацию → часы работы → услуги/цены/длительность → мастеров и доступность → публикует ссылку и Telegram-бота → делает тестовую бронь. Целевое UX-время 10–15 минут для простого салона, проверяемое тестом.

## UX принципы
- Клиент не обязан разговаривать с AI: календарь и каталог всегда доступны.
- Переход между ботом, страницей и Mini App не должен дублировать запись.
- Мобильная админка не урезает критически важные действия; сложные отчёты допускают desktop-first UX.
- Ошибки и отсутствие слотов понятны без инструкций.
- Виджет встраивается в сайт, отдельная страница и Mini App используют общий компонентный слой, но отличаются transport/auth shell.
- Отзывы мастеров возможны в расширении, но требуют политики модерации и подтвержденного происхождения.

## Референсы качества интерфейса (пожелание владельца, 2026-11-13)
- **Telegram (мобильные и desktop-клиенты)** — референс субъективной отзывчивости, быстрых переходов, естественных жестов и немедленной обратной связи.
- **Altare.gg (панель хостинга)** — референс субъективно приятного, быстрого и функционального рабочего интерфейса.
- Это **референсы качества UX**, а не утверждение копировать внешний вид, визуальный язык, брендинг, конкретные анимации или внутренние технологии этих продуктов. Их интерфейсы пока не подвергались нашему измерительному аудиту.
- Цель Cookie: лёгкая навигация, короткие пользовательские пути, быстрый отклик на нажатия/изменения календаря, устойчивое состояние во время загрузок и понятные подтверждения действий.
- Для критических действий (создать/перенести бронь) мгновенно показывать обработку, но **не показывать успех до подтверждения сервера**. Для безопасных локальных действий оптимистичный UI допустим.
- Интерфейс должен приятно работать не только на быстром телефоне: бюджетные Android, Telegram WebView и обычный мобильный браузер — обязательные тестовые среды.

## Исследования до UI freeze
Провести 5–8 тестов онбординга и записи на макетах; интервью с 5–10 салонами о боли, расписаниях, ручных обращениях и спросе на независимость. Зафиксировать фактическое время и ошибки, а не оценку «красиво/некрасиво».
