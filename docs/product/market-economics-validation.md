## 2. Какие гипотезы реально отличают Cookie

| Проверяемая гипотеза | Измерение/эксперимент | Не считать успехом |
|---|---|---|
| Telegram-first запись в 2–10-мастерном салоне уменьшает ручные обращения | В пилоте замерить долю booking через bot без участия администратора, ручные минуты до/после и долю завершённых попыток | «Салону понравился Telegram» без реальных Booking |
| Onboarding проще конкурентного | Дать владельцу без обучения самостоятельно настроить услуги+мастеров+график и получить первую тестовую Confirmed; замерить время/ошибки | Обещанные 10–15 минут без теста |
| Единый календарь, надёжная запись и no-double booking решают операционную боль | Реальные конфликты/ошибки до/после, количество обращений к поддержке, восстановление после недоставленного уведомления | Скрытые двойные записи в разных каналах |
| Персональная цена и понятные условия ценнее условно бесплатной альтернативы | Сравнить предложенную стоимость с фактом отдельного платного consent и **реальной оплатой** после 30 дней, причины отказа | Позитивное интервью/регистрация/устное обещание оплатить |
| Возможность переносимости/self-hosted ценна отдельным клиентам | Найти клиентов с требованиями к размещению/данным, проверить юридическую/техническую реализуемость и готовность оплатить установку+поддержку | Просто техническая возможность контейнеризации |

**Предложенный эксперимент до прайса:** провести **не менее 10 целевых интервью** (этот критерий уже указан в [бизнес-модели](business-model.md)); собрать текущие расходы на CRM, размер команды, объём записей/мессенджеров, 3 наиболее болезненных ручных операции и ожидаемые ограничения. Отдельно сформировать короткий список тех, кто готов испытать Cookie по индивидуальному офферу. Число пилотных салонов и реальные цены **не принято**; агент не может заменить ответы салонов выдуманными цифрами.

## 3. Юнит-экономика — модель исходных данных (не fictitious prices)

Пусть:
- `N` = число платящих Organizations; анализ сценариев `N=10/50/200`.
- `T` = число одновременно бесплатных trial Organizations + posttrial inactive, не дающих выручку, но хранящих данные.
- `P_i` = **фактическая** индивидуальная месячная выручка с платного салона i по согласованному офферу (не публичный прайс).
- `H(N,T)` = все fixed + scale-dependent расходы инфраструктуры: compute, Postgres, backups, logs, provider infrastructure в РФ.
- `V_i(B_i,M_i)` = переменные расходы i при `B_i` Booking и `M_i` сообщений/отправок (provider/SMS fees, DB/storage, payment processing).
- `S_i` = support+onboarding time × его фактическая стоимость; `CAC_i` — стоимость получения платного салона.

**Доходность периода (simplified contribution):**
```text
MRR(N)              = Σ_{i=1..N} P_i
DirectCost(N,T)      = H(N,T) + Σ_i [V_i(B_i,M_i) + S_i] + costs_of_unpaid_organizations(T)
Contribution(N,T)    = MRR(N) - DirectCost(N,T)
ContributionMargin   = Contribution / MRR  (только если MRR > 0)
CACpayback_i_months  = CAC_i / positive_monthly_contribution_i
```

**Три обязательных сценария (значения заносить только после измерений):**

| Платные салоны | Выручка | Общие расходы и риски |
|---|---|---|
| **10** | `ΣP_i` для 10 | Низкий объём оплаты может не покрыть инфраструктурный минимум, поддержку, миграции и бэкапы |
| **50** | `ΣP_i` для 50 | Доля неоплаченных trial/deactivated tenants, рост notifications и запросов в БД |
| **200** | `ΣP_i` для 200 | Нагрузка на scheduling/notifications, стоимость саппорта, мониторинг, DB partitions/indices без booking quota |

Для каждого `N` отдельно записать `T`, число действующих мастеров `2/5/10`, распределение Booking в месяц и стоимость каждого канала. Не вводить коммерческий booking cap: **высокая нагрузка — риск инфраструктуры, а не скрытая тарифная квота**. Стресс-тесты F1/F2 выполняются на synthetic traffic с фактическими DB/CPU/latency метриками.

**Правило evidence:** не подставлять предполагаемую цену 690/1490 ₽ или 24900 ₽ как согласованную. Они остаются RESEARCH placeholders; конкретный оффер каждому реальному салону фиксировать до регистрации, оплачиваемые деньги — только через доказанный добровольный opt-in.

## 4. Структура данных пилота (без сбора реальных контактов в F0)

Минимальные записи для анализа:
- `pilotLeadId` (без персональных контактов в аналитической выгрузке), сегмент, размер unique bookable команды, число филиалов, текущий booking tool, причина перехода.
- `offerVersion`, период/цена/объем уровня, timestamp до регистрации, acknowledged status, дата создания Organization и endAt trial.
- `configCompletedAt`, `firstRealBookingAt`, доля самостоятельных web/TG Booking, число ошибок и отмен.
- `paidConsentAt`, `firstPaidInvoicePaidAt`, сумма действительной оплаты, cancel/refusal reason.
- `infraCost`, `notificationsCost`, `supportMinutes`, итог `contribution` — по salongroup/cohort с конфиденциальными финансовыми данными в защищённом доступе.

**Критерий осмысленного решения о едином публичном прайсе (PROPOSED):** конкурентные различия подтверждены объективными тестами, для различных master tiers оценена маржа, есть фактические предложения и реальные оплаты, известны причины отказов и нужная поддержка. **Не обещать определённую конверсию/ROI без данных.**
