# Безопасность, доступы и персональные данные

**Статус: PROPOSED / обязательный security review перед F2.** Не является юридическим заключением.

## Модель угроз
Акторы: клиент, сотрудник нескольких организаций, админ, владелец, анонимный посетитель, администратор сервера, внешний AI/messenger provider. Главные риски: доступ к чужим броням, утечка клиентской базы, обход permissions через бота/AI/MCP, cross-tenant data leak, захват токенов гостевого управления и компрометация Telegram.

## Требования
- Identity (кто действует) отдельно от Customer (кто посещает салон) и роли (что разрешено).
- Server-side authorization на **каждый** read/write, включая отчёты, фоновые задания, AI tool calls и MCP.
- Tenant scope обязательный в query/command; запрет менять tenant из клиентского body; фильтрация результата по tenant.
- Ссылки для гостевого управления — одноразовые/короткоживущие либо с OTP-подтверждением, rate limit.
- Telegram Mini App: серверная HMAC проверка initData и auth_date; не доверять initDataUnsafe; пользовательская связка с Customer через подтверждённые шаги.
- Телефон и email собирать только когда нужны для услуги/подтверждения. Рекламное согласие не подменяет договорную обработку.
- Secrets не хранить в репозитории/логах, ротация, encryption in transit, бэкапы защищены.
- Не отправлять персональные данные в LLM без согласованной политики и законных оснований; минимизировать prompt context и редактировать logs.
- AI и голос: минимальные scopes, явное подтверждение mutating actions, подробный audit log.
- Защита API: rate limiting, validation, CSRF в зависимости от метода авторизации, origin restrictions, webhook signature validation, replay protection.
- Владельцы не получают доступ к базе других организаций; поддержка поставщика — только через отдельный контролируемый режим доступа.
- Права сотрудника ограничены своей организацией и своими сменами/бронями в соответствии с ролью.

## РФ / 152-ФЗ
Коммерческое размещение и первичный сбор ПДн граждан РФ требуют проверки локализации баз, обязанностей оператора и отношений оператора/обработчика, политики обработки, сроков хранения и удалений, уведомления регулятора при необходимости. Демонстрации на бесплатных зарубежных ресурсах допустимы только с синтетическими данными до юридической проверки. Договорный self-hosted не отменяет обязанностей салона.

## Ограничение видимости CRM для мастера (2026-11-14)
**ACCEPTED:** базовая staff роль не даёт доступ ко всей клиентской базе филиала. Мастер получает доступ только к своим бронированиям и соответствующим клиентам по подтверждённой staff-booking relation и location scope. Доступ к телефону, истории и заметкам — отдельные настраиваемые права организации; отсутствие права запрещает выдачу поля через все каналы и экспорты.

**Контроль:** полевая фильтрация ответа/DTO на backend; проверка Customer/Booking по tenantId+locationId+StaffProfile; запрет поискового перечисления и bypass через AI/Telegram/MCP. Отзыв роли, смена мастера и увольнение прекращают доступ по актуальной policy. Чувствительные заметки требуют отдельной классификации и сроков хранения.

**Негативные тесты:** мастер А не видит клиентские контакты мастера Б, не может запросить их по известному Customer ID, получить через API search/export или в чате. Дополнительная роль администратора филиала A не даёт аналогичных прав в филиале B.

## Security acceptance
- Межтенантные tests чтения/изменения/exports.
- AuthZ tests всех commands, включая AI/MCP.
- Backup restore encrypted, policy на retention/export/delete.
- Пентест базовых сценариев/OWASP, security checklist перед публичным запуском.
- Матрица доступа owner/admin/staff/client/guest утверждена в виде отдельной задачи.
